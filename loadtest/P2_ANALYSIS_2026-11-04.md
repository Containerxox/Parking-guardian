## 1. CPU 공정성 검증
**실제 설정 [관찰: config 매니페스트 + 클러스터 `kubectl get deploy`]**
| 항목 | Phase 1 inference | Phase 2 Worker |
|---|---|---|
| Replica | HPA 2~3 (측정 때 `p3.py pause` 로 2 고정) | KEDA: 공존 min 0 / max 1, 비교 구성 min 1 / max 3, 측정 중 `paused-replicas` 로 N 고정 |
| 메인 컨테이너 `requests.cpu` / `requests.memory` | 1000m / 1.5Gi | 1000m / 1.5Gi |
| `limits` | memory 2Gi, **CPU limit 없음** | memory 2Gi, **CPU limit 없음** |
| 초기화 컨테이너(모델 받기) | `requests.cpu` 100m (시작할 때만) | 100m (시작할 때만) |
| `TORCH_NUM_THREADS` | 1 (inference-config) | 1 (worker-config, "inference-config 와 같은 시작값") |
| 스레드를 실제로 고정하는 방법 | `wsgi_inference.py` 가 torch 를 import 하기 **전에** `OMP_NUM_THREADS`·`MKL_NUM_THREADS` 를 정하고, `torch.set_num_threads(1)` 도 호출 | `flask judge-worker`: `torch.set_num_threads(1)` **만** 호출(`apply_thread_env` 는 inference 서비스 진입점에서만 호출됨) |
| 같은 노드의 다른 Pod | backend 2×200m, relay 50m, frontend 50m, 애드온 | 같음 |
- **합계**: Phase 1 AI = 2 × 1000m = **2000m**, Phase 2 AI(Worker 2) = 2 × 1000m = **2000m**. 이전 보고의 "총 4000m" 은 **양쪽을 더한 값을 한 쪽 값처럼 쓴 오류**였다. config 저장소 `loadtest-execution-plan-2026-11-04.md` 의 "AI 자원" 행을 고쳤다.
- 노드 하나의 할당 가능 CPU 는 1930m 이라 AI Pod 하나가 약 52 % 를 **예약**한다. 한 노드에는 AI Pod 가 하나만 들어간다(R7).
- **requests 와 실제 사용량은 다르다**: requests 는 스케줄러의 자리 예약이고 경합이 있을 때 CPU 몫(shares)을 정한다. CPU limit 이 없어서 노드가 한가하면 한 Pod 가 1000m 을 넘게 쓸 수 있다.
  관찰: 지금 유휴 상태 inference 1m·backend 3m·relay 4m. E2E 때 Worker 는 최대 710m·891Mi(10 s 표본 12개, 사진 2장). Phase 1 최종 보고서는 inference Pod 가 부하에서 약 1 코어로 포화했다고 기록했다.
- **공정성 판단**: "같은 예약 자원" 비교는 성립한다. 그러나 **같은 실효 CPU 를 보장하지는 않는다**.
  1. 스레드 고정 방식이 다르다(위 표). Worker 는 OpenMP/MKL/OpenCV 네이티브 스레드를 1개로 묶지 못했을 수 있고, CPU limit 이 없으니 1 코어를 넘게 쓰면 Worker 에 유리하다 **[미확인]**. 포화 시험(W)에서 Worker CPU 표본이 requests 의 1.2배를 지속적으로 넘으면 "Worker 가 더 많은 CPU 를 썼다"고 적고 공정 비교로 쓰지 않는다. 확정은 Pod 안 스레드 수 확인(별도 승인).
  2. 사진 한 장당 하는 일이 다르다: Phase 1 = backend→inference HTTP 전달 + 입장 제어, Phase 2 = S3 PUT·GET + DB 쓰기 + SQS. 같은 CPU 를 써도 AI 에 쓰는 비중이 다르다 → "구성요소별 CPU / 완료 사진 수"를 함께 보고한다.
  3. backend·DaemonSet 이 같은 노드를 나눠 쓴다 → Pod 배치와 노드 CPU 를 회차마다 기록한다.
- 새 도구: `p2_watch.py` 가 15 s 마다 `kubectl top pods` 표본을 타임라인에 넣고, `p2_watch.py resources --out timeline.jsonl` 이 앱별 CPU 최대·평균과 requests 대비 비율을 낸다 [시험].

## 2. 간헐적 테스트 실패 분석
- **관찰**: 반복 실행(약 14회 중 1회)에서 통합 시험 1건이 실패했으나 당시 출력을 남기지 못했다. 이후 12회는 통과했다.
- **조사**: (1) 시험 코드의 타이밍 의존 단언을 찾았다 — k6 종료 코드 `== 0`(오류·재시도·직렬화·파이프라인 시험), 절대 간격 상한(`max(gap) < 0.9`), 지연 상한(`p95 < 2.0`). (2) 시험 PC 에 CPU 부하(8코어에 바쁜 프로세스 12~24개, `tools/stress_cpu.py`)를 걸고 같은 시험을 돌렸다.
- **재현됨 [시험]**: 부하 아래에서 오류·재시도 시험 2건이 실패했다. 출력: `p2: sent=57 … dropped_slots=3`, `sent=34 … dropped_slots=2` — k6 가 목표 시각보다 `LATE_TOL_MS`(1000 ms) 넘게 늦어 슬롯을 건너뛰었고, 임계값 `p2_dropped_slots == 0` 실패로 **k6 종료 코드가 99** 가 됐다. **도구가 "무효 회차"를 의도대로 알린 것**이다. 시험이 "회차가 유효하다(종료 코드 0)"를 기능 검증에 섞어 놓은 것이 결함이었다.
- **원래의 1건**이 정확히 이것이었는지는 **[미확인]**(출력이 없다). 증상은 일치한다.
- **모의 서버 동시성**: 공유 상태(DB 연결, 장비별 진행 중 수, 통계)는 한 락 안에서 바뀌고, "장비별 최대 동시 요청 1"은 서버가 측정한 값이라 시험 PC 의 부하와 무관하게 성립한다. 부하에서 깨진 것은 서버 정합성이 아니라 k6 의 시간 정확성이었다.
- **고친 것(제한 시간을 늘리지 않았다)**: ① 회차 유효성과 기능을 분리 — 종료 코드가 0 이거나 `99 + P2DROP 있음 + 4xx/연결 실패 0` 이면 기능 단언을 계속 검증(다른 임계값 실패는 그대로 실패). ② 절대 간격 단언을 계약 단언으로 — 계획 간격(`planned_ms`)이 정확하다 / 실제 전송은 계획보다 빠르지 않고 `LATE_TOL_MS`+50 ms 이내(더 늦으면 건너뛰고 P2DROP) / 건너뛴 슬롯이 없을 때만 평균 간격이 계획과 같다. 전송 수는 "계획 − 건너뛴 수". ③ 지연은 하한 = 서비스 시간 100 ms, 상한 = 사전 등록 계약 10 s. ④ 일정 기준 시각을 `setup()` 종료가 아니라 시나리오 실제 시작(`exec.scenario.startTime`)으로 — 첫 실험에서 k6 가 시나리오를 늦게 시작해 슬롯 31개가 버려진 것이 계기.
- **재측정**: 수정 뒤 같은 부하 아래에서 그 시험 4건이 통과, 부하가 없을 때 연속 6회 통과 [시험].
- **남은 위험 [미확인]**: 실제 AWS 시험에서도 PC 가 바쁘면 같은 방식으로 슬롯이 버려져 회차가 무효가 된다 — 시험 중 PC 의 다른 작업을 끄고 k6 프로세스 CPU 70 % 미만 규칙을 지킨다.

## 3. 테스트 데이터 증가량 검증
`k6/plan_counts.js` 가 `scenarios_p2.js` 와 같은 함수(`buildProfile`, `deviceSlots`)로 전송 계획 수를 계산한다 [시험].
| 항목 | 값 |
|---|---|
| S1 이상값 | 5.2 × 3.107 × 180 s = 2,908.1 장 |
| **S1 실제 계획 전송 수** (C=3.107) | **2,911장** = 112 / 280 / 448 / 560 / 672 / 839 (장비 3대: 973 / 970 / 968; 장비 5대여도 합 2,911) |
| 사진 한 장 | `sample_a` 369,857 B |
| S3 `inbox/` (S1 1회) | 2,911 × 369,857 B = **1,076,653,727 B ≈ 1.08 GB**. S1 × 3 = 약 3.23 GB |
| DB 행 증가 (S1 1회) | `detection_jobs` +2,911, `detection_results` +2,911, `device_sessions` +3 = **5,825행**(이전 "약 5,800" 일치). S1 × 3 = 17,475 + 9 |
| 그 밖의 쓰기 | 장비 행 UPDATE 사진당 2회(접수 때 신호, 판정 때 반영), 작업 행 UPDATE 3~4회 — 행 수는 늘지 않고 죽은 튜플만 생긴다. 위반·알림·확인 명령·감사 로그는 **허가 판정에서는 생기지 않는다** [시험: 실제 백엔드 코드] |
| SQS | 메시지 2,911개(FIFO, 중복 제거 id = job_id), 전송·수신·삭제 각 약 2,911회 + KEDA 폴링(15 s) |
| S3 요청 | 사진당 PUT 1 + GET 1(Worker). violations/ 복사는 위반일 때만 |
| RDS 용량 | 행당 수백 B [추정, 행 크기 미측정] → S1 1회 수 MB. 20 GB 에 비하면 무시 수준 |
- **장비별 FIFO 직렬화**: 데이터 양은 바뀌지 않는다(접수는 큐 길이와 무관하게 202). 영향은 **시간**이다 — 장비 한 대는 한 번에 1건이라 장비당 처리 상한 ≈ 1/서비스시간(추론 약 0.7 s [관찰: E2E 715·688 ms] → 약 1.4 장/초 [추정]). 장비 3대·Worker 2 면 처리 능력 약 2.9 장/초 [추정]이라 1.0C(3.107) 부터 대기열이 쌓인다 [계산·추정]: 1.0C 약 +44건, 1.2C 약 +157건, 1.5C 약 +324건(Worker 2 기준; 1.5C 는 장비당 1.55 장/초 > 1.43 이라 Worker 를 늘려도 장비 직렬화 한계). 이 단계들에서 10초 이내 판정률이 100 % 아래로 내려가는 것은 정상 결과일 수 있다.
- **S3 7일 수명 주기 [관찰: Terraform `storage_s3.tf`, `inbox_retention_days` 기본 7]**: 규칙은 접두어 `inbox/` **하나**에만 걸린다(만료 = 영구 삭제, 버전 관리 꺼짐). `violations/` 에는 규칙이 없다. 허가 판정 시험은 `inbox/` 만 만든다. 큐 보존이 inbox 보존보다 짧아야 한다는 사전 검증이 있다.
- **기존 위반·알림에 영향** [시험: 실제 백엔드 코드 + 가짜 큐, `test_smoke_semantics.py`]:
  - 활성 사건이 없는 장비에 허가 사진을 아무리 보내도 위반·알림·이력은 늘지 않는다.
  - **활성 사건(`ended_at IS NULL`)이 있는 장비는 상태가 RESOLVED 여도 영향을 받는다.** 무신호 10분 초과 뒤 첫 사진이 사건을 `SIGNAL_LOST` 로 종료하고, 허가 사진 3연속은 `STICKER_DETECTED` 로 종료하며, 둘 다 `violation_history` 에 1행을 더한다.
  - **지금 이 상태인 장비 [관찰: 읽기 전용 조회]**: machine 1 `RPI-A-GANGNAM-01`(위반 #3), machine 6 `RPI-E2E-TEST-01`(위반 #5). 두 장비의 마지막 신호는 이미 10분 넘게 지났으므로 **첫 사진 하나로 #3 또는 #5 가 바뀐다.** (#5 는 관리자 UI 시험에서 처리 완료한 시험 데이터다.)
  - 결론: 데모 장비 1 은 쓰지 않는다. 시험 장비 6 을 부하에 쓰면 #5 의 `ended_at`/`end_reason` 과 이력이 바뀐다 → 새 장비만 쓰는 것을 권한다([P2_SMOKE_PLAN.md](P2_SMOKE_PLAN.md) 2절).
- **RUN_ID 로 구분**: 사진마다 `event_id` 앞 8자리가 run tag, 단계 번호도 같은 id 에 있어 같은 장비·DB 에서 재측정해도 회차별로 갈린다. `p2_collect.py runs --source kubectl --since <시각>` 이 회차별 작업 수·상태·미완료 나이를 읽기 전용으로 보여 준다 [시험].
- **실패 뒤 미완료 작업 확인**: `runs` 의 `unfinished`/`oldest_unfinished_age_s`, 보고서의 `unfinished`/`job_status_counts`, `p2_collect.py sqs`, `p2_watch` 의 DB 표본. 미완료 작업은 지우지 않는다 — Relay·Worker 가 계속 처리한다.

## 4. 결과 파일의 Git 관리
- **구조**: 앱 리포 `develop` 의 `loadtest/` 에 k6 스크립트·분석 도구(코드)가 있고, 측정 결과 원본은 저장소에 올리지 않는다. `docs/*` 규칙이 `docs/measurements/phase2/...` 를 이미 무시하고, 아래 산출물 규칙을 `.gitignore` 에 명시했다.
- **제외 규칙**(`.gitignore`): `loadtest/` 아래 산출물(k6 기본 출력 `p2-out/`, `*.sqlite`, `sends.log`, `points.json`, `timeline.jsonl`, `ABORT.flag`, `p2-*.csv`, `p2-report.json`, `compare.csv`, `baseline*.json`), `*.bak-*` 백업, 양 Phase 의 `results/`·`eks/`, 장비 키·토큰 파일.
- **코드와 데이터 구분**: 코드(`loadtest/k6/*.js`, `loadtest/tools/*.py`, 문서)는 제외하지 않았다 — 신규 파일은 `git status` 에 `??` 로 보이고 커밋 여부는 사용자가 정한다. 결과·원자료는 `docs/measurements/phase2/results/<날짜>-<시나리오>-<n>/` 한 곳에 모은다.
- **비밀 포함 여부**: `sends.log`/`p2-attempts.csv` 에는 event_id·seq·상태·지연만 있고 키·토큰·비밀번호는 없다(가짜 키 시험으로 k6 출력·로그·요약·수집 결과 전부 확인). `timeline.jsonl` 에는 Pod·노드 이름이 있다(비밀은 아니지만 공개 금지). 장비 키는 `p2_devices.py launch` 가 자식 프로세스 환경변수로만 넘긴다.
- **포트폴리오 요약만 따로**: `portfolio_summary.py --p1 … --p2 … --out <폴더> --label …` 가 집계 숫자(단계별 도착률·처리량·10초 이내 판정률·실패율·지연 분위수·표본 수와 정의·유효성)만 `summary.md/json` 으로 쓴다. event_id·Pod 이름·장비 일련번호·IP·호스트·계정 형태가 있으면 파일을 쓰지 않고 중단한다 [시험]. 공개 자료로는 이 요약을 검토한 뒤 복사한다.
