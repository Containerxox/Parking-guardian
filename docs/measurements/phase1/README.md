# Phase 1 부하 테스트 사전 등록

- 상태: **고정 v1** (2026-10-31, E0 실행 전). 고정 뒤 바꾸는 내용은 아래 "변경 기록" 에 이유와 함께 남기고, 결과를 본 뒤 바꾼 것은 그렇다고 적는다.
- 실행 도구: `loadtest/`(k6 스크립트와 실행 절차 `loadtest/README.md`). k6 v2.3.0. 지표 정의(Phase 1 / Phase 2 비교)는 `loadtest/README.md` 2.3절.
- 대상: ADR 0018(동기식 API / AI 서비스 분리). 설계 원문은 `docs/design/ARCHITECTURE_EVOLUTION.md` 4장(실험), 5장(부하 테스트).
- 목적: 안전한 운영 설정(타임아웃, 동시 상한, 재시도 상한)을 갖춘 Phase 1 의 실제 한계를 잰다. 결과가 Phase 2(ADR 0019)의 근거가 되지 않으면 그대로 기록한다.

## 1. 무엇을 미리 고정하는가

| 고정하는 것 | 이유 |
|---|---|
| 가설과 반대 결과 조항 (2절) | 결과를 보고 가설을 고르지 않기 위해 |
| 통과 기준 (3절) | 결과를 보고 기준을 바꾸지 않기 위해 |
| 상한 값의 **선택 규칙** (4절) | 값 자체가 아니라 값을 고르는 방법을 미리 정해, 공식 구성이 측정 결과에 맞춰 유리하게 골라지지 않게 |
| 시나리오와 부하 정의 (5절) | Phase 2 에 같은 프로필을 그대로 쓰기 위해 |
| 보고 형식 (7절) | 불리한 결과를 빼지 않기 위해 |

## 2. 가설과 반대 결과 조항

| 가설 | 측정 | 성립하지 않으면 |
|---|---|---|
| H1. 사진 부하가 늘면 일반 API 지연이 늘어난다 | S1: 사진 도착률 단계별 일반 API p95 | 동시 상한이 일반 API 를 지킨 것이다. Phase 1 의 한계는 "과부하 시 사진 거절·유실" 로 기록한다 |
| H2. AI 장애가 일반 API 가용성에 영향을 준다 | S5(a)(b): 일반 API p95·오류율 대 S0 | readyz 분리의 성과로 기록한다 |
| H3. 처리 용량을 넘으면 탐지 요청이 실패한다(거절·타임아웃) | S3: 1.2C 지속 부하의 사진 성공률 | 거절이 0 이면 Phase 2 의 근거를 확장 비용·운영 유연성으로 옮기거나 Phase 2 범위를 줄인다 |
| H4. inference 를 늘리면 처리량이 Pod 수에 비례해 는다 | E3 | 비례하지 않는 원인(노드 CPU, 네트워크, DB)을 기록한다 |

## 3. 통과 기준

| 항목 | 기준 |
|---|---|
| 일반 API p95 | < 500 ms |
| 일반 API 오류율 | < 1% |
| 사진 성공률 (장비가 200/201 을 받은 비율) | 0.8C 이하에서 ≥ 99% |
| 부하 발생기 (무효 판정) | 아래 중 하나라도 해당하면 그 회차는 무효로 기록하고 다시 한다: k6 `dropped_iterations` > 0, k6 프로세스 CPU ≥ 70%, 부하 단계가 오를 때 k6 p95 와 서버 p95 의 차이만 커짐 |

C = E3 에서 잰 서비스 전체 처리 용량(장/초).

## 4. 상한 값 선택 규칙

| 번호 | 대상 | 후보 | 부하 | 규칙 |
|---|---|---|---|---|
| T1 | `INFERENCE_MAX_WAITING` | 0, 1, 2, 4 | inference 단독, 1.2C₁ (C₁ = Pod 1개 용량) | 처리량이 최대의 98% 이상인 후보 중 가장 작은 값 |
| T2 | `AI_CLIENT_MAX_CONCURRENCY` | 2, 4, 6 (API 스레드 8) | S1 혼합 부하의 1.5C 단계 | 일반 API p95 < 500 ms 와 오류율 < 1% 를 지키는 후보 중 사진 성공률이 가장 높은 값. 동률이면 작은 값 |
| T3 | `AI_CLIENT_DEADLINE` | 계산 | — | E0 p99 × (1 + T1 결과) + 1초, 초 단위 올림 |
| T4 (선택) | API 스레드 수 | 4, 8, 16 | S1 | T2 와 같은 규칙 |

규칙에 맞는 후보가 없으면 그 사실을 기록하고 가장 가까운 후보를 쓴다. 이 단계에서 정한 값이 Phase 1 공식 구성이다.

**X1 (대조 실험, 공식 구성 아님)**: 동시 상한 = 스레드 수, 대기 상한 = 무제한. S1 프로필. 상한이 무엇을 막아 주는지 보이기 위한 실험이며 보고서에서 별도 절로 둔다.

## 5. 실험과 시나리오

### 5.1 소규모 실험 (inference 단독, k6 closed-loop)

| 번호 | 바꾸는 것 | 측정 |
|---|---|---|
| E0 | 없음 (Pod 1, worker 1, torch 스레드 1 = **시작값, 운영값 아님**, 동시 1). 시작할 때 Pod 안의 torch 기본 스레드 수(`torch.get_num_threads()`)와 대기 줄 끝 사진의 응답 시간(마감 근접 여부, 설계 4.2)을 함께 기록 | 장당 서비스 시간 분포, 최대 처리량 C₁ |
| E1 | torch 스레드 1 → 2 (**운영값은 여기서 정한다.** 2 vCPU 노드라 4 이상은 후보에서 제외. 로컬 PC 의 1/2/4 측정은 참고용) | 처리량, p95, CPU. 함께 기록: 게이트가 디코드까지 직렬화한 영향(`pg_inference_stage_seconds{stage="decode"}` 비중, 디코드가 락 밖이던 Prototype 과의 처리량 차이) |
| E2 | 같은 노드에 inference Pod 2개(요청 각 600m) | 노드당 처리량, 지연, 메모리 |
| E3 | Pod 1 → 2 → 3 (노드마다 1개) | 서비스 전체 처리량 C |

### 5.2 부하 시나리오

공통: 일반 API 워크로드는 로그인 1회 뒤 위반 목록, 대시보드 요약, 알림 조회 반복. readyz 1 req/s 별도 기록. 사진은 `sample_a`(허가 판정) 100%, 위반 사진(`sample_b`) 0%(사용자 결정 2026-10-31. 위반 확정 경로 DB·S3·알림은 이 baseline 에 포함하지 않고 테스트 전용 데이터와 별도 시나리오에서 따로 검증한다). 장비 키 3개(기존 기기 2·4·5번. 1·3번은 진행 중인 위반 1~4번 보호를 위해 사용하지 않는다). 관리자 요청은 COMPANY_ADMIN 계정 하나로 통일한다. 각 시나리오 3회, 중앙값과 범위. 한 회차 15분 이내.

| 번호 | 내용 | 비교 |
|---|---|---|
| S0 | 일반 API 5 req/s, 5분, 사진 0 | 기준선 |
| S1 | 일반 API 5 req/s + 사진 0.2C → 0.5C → 0.8C → 1.0C → 1.2C → 1.5C (각 3분) | A |
| S2 | 사진 20건 동시 후 유휴 | A |
| S3 | 사진 1.2C, 10분 지속, 이후 회복 관찰 | A |
| S4 | S1 프로필, HPA 켬. 노드 3대 용량 때문에 프로필을 나눈다: (가) inference 최대 3 + api 최대 2, (나) api 최대 3 + inference 최대 2, (다) 둘 다 최대 3 ("일반 API 만 3배" 부하는 (나)). 최대 3 은 실험 환경의 시작 기준이다. (다)는 노드 여유가 30m 뿐이라 재구축 직후 노드별 요청 합을 확인한 뒤 실행한다. Pending 이 생기면 결과로 기록 | B |
| S5 | **주입 실험**: (a) inference 0개 (b) inference 지연 주입(테스트 전용 설정) (c) api Pod 1개 삭제 | A |
| V1 | 배치 기록: 배포 직후, 각 시나리오 전후, 롤링 뒤 inference·api 가 어느 노드에 있는지 | — |
| V2 | 부하 중 inference 가 있는 노드 1대 cordon + drain (분산 상태) → 서비스 지속, PDB, 재배치·Ready 시간 | A |
| V3 | **주입 실험**: inference 2개를 한 노드에 모은 뒤 그 노드 drain → 탐지 중단 시간, 관리자 API 영향 | A |
| P1 (선택) | S1 을 api 2개를 inference 없는 노드에 고정해 1회 → 기본 배치(공존)와 비교. 그 회차만 노드 단위 고가용성 포기 | A |

- 비교 A(동일 자원): HPA 끔, api 2 + inference 2 고정.
- 비교 B(운영 자동 확장): HPA 켬, 같은 노드 3대.
- k6 위치: 5.1(E0~E3)과 T1 은 클러스터 안 작은 k6 Job(CPU 요청 100m). 5.2 와 T2·X1 은 로컬 PC 에서 ALB 로. 두 위치가 같은 스크립트 파일을 쓴다.

### 5.3 관찰 항목 (판정 기준이 아니라 기록 항목)

- **AI 응답 대기 중 API 의 DB 연결 점유**: AI 를 기다리는 동안 요청이 트랜잭션을 연 채 DB 연결을 잡는다(코드로 확인, 미측정). S1/S4 중 `pg_stat_activity` 의 `idle in transaction` 수를 AI 호출 시간·`pg_ai_client_in_flight` 와 함께 기록한다. 동시 호출 상한이 이 수를 제한하는지 본다.
- 최대 상태(api 3 + inference 3)에서 롤링 업데이트의 지연 (surge Pod Pending, `maxUnavailable 0` 이라 서비스는 유지).
- AI 가 없을 때 탐지 503 이 나오기까지의 시간(로컬 Docker 는 DNS 때문에 8.3~8.6초. Kubernetes Service 는 다를 것으로 예상, 미확인).
- 재구축 직후 `amazon-cloudwatch` 의 구성 요소와 CPU 요청 합, 노드별 요청 합.
