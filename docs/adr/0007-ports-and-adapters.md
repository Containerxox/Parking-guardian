# 0007. 추론, 사진 저장, 알림 발행을 Adapter로 분리한다

- 상태: 결정됨 (2026-10-01)

## 문제

이 프로젝트는 단계적으로 바뀐다. AI 추론은 같은 프로세스에서 별도 서비스로, 사진 저장은 로컬 디스크에서 S3로, 알림은 요청 안에서 바로 처리하는 방식에서 대기열과 별도 작업자로 옮겨 간다. 이 세 가지가 업무 코드에 직접 박혀 있으면 단계가 바뀔 때마다 업무 코드를 다시 고쳐야 한다. 기존 코드는 실제로 추론, 파일 저장, DB 기록이 한 함수 안에 섞여 있었다.

## 결정

Backend는 세 가지를 인터페이스로만 호출한다. 구현은 설정에 따라 바꿔 끼운다.

| 역할 | 지금 | 이후 |
|---|---|---|
| 추론 (`inference`) | 같은 프로세스에서 YOLOv5 실행, 테스트용 mock | 별도 추론 서비스를 HTTP로 호출, Timeout과 재시도 |
| 사진 저장 (`storage`) | 로컬 디스크 | S3, 조회는 Presigned URL |
| 알림 발행 (`publisher`) | 요청 안에서 바로 알림 생성 | SQS에 이벤트를 넣고 작업자가 처리, 실패 시 DLQ |

지금부터 이후 구조를 염두에 둔 부분도 있다.

- 사진의 Key를 이미 S3 방식으로 만든다: `violations/company-1/parking-lot-3/2026/10/01/violation-123.jpg`. DB에는 Key만 저장한다.
- 사진 조회는 로그인 헤더 없이 열리는 짧은 수명의 서명 주소를 발급하는 방식이다. S3의 Presigned URL과 같은 모양이라 화면 코드를 바꿀 필요가 없다.
- 알림 생성은 같은 호출이 두 번 와도 중복되지 않게 UNIQUE 제약(위반, 관리자, 채널)을 뒀다. 대기열은 같은 메시지를 두 번 전달할 수 있기 때문이다.

## 부분 실패를 견디는 순서

위반이 확정되면 순서를 지킨다: **사건 저장 → 사진 저장 → 알림 발행.** 뒤 단계가 실패해도 앞 단계를 되돌리지 않고 실패를 이력에 남긴다.

| 실패 | 결과 |
|---|---|
| 사진 저장 실패 | 위반은 남는다. `image_status=FAILED`, 이력에 기록. 알림은 계속 진행 |
| 알림 발행 실패 | 위반과 사진은 남는다. 이력에 기록. 관리자는 알림 없이도 처리할 수 있다 |
| 추론 실패 | 아무것도 저장하지 않고 503. 장비가 다음 주기에 다시 보낸다 |

알림 장애가 탐지 장애로 번지지 않는다는 요구를 이 순서로 지킨다.

## 결과

- 얻은 것: 테스트가 torch 없이 mock 추론으로 돈다. 이후 단계에서 Adapter만 추가하면 된다. 부분 실패를 테스트로 재현할 수 있다.
- 감수한 것: 파일과 간접 호출이 늘었다.

## 근거

- `backend/app/adapters/` (`inference.py`, `storage.py`, `notifier.py`)
- 순서와 실패 처리: `backend/app/api/device.py`
- 테스트: `backend/tests/test_violation_flow.py` 의 사진 저장 실패, 알림 실패, 추론 실패 세 가지

## 한 줄 설명

추론, 사진 저장, 알림 발행을 Adapter로 분리해 이후 별도 서비스, S3, SQS로 바꿔 끼울 수 있게 했고, 뒤 단계가 실패해도 위반 기록은 남도록 순서를 정했습니다.
