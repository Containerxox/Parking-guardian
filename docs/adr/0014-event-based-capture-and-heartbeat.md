# 0014. 장비가 점유 변화를 감지해 사진을 보내고, 연결 상태는 Heartbeat로 알린다

- 상태: **결정됨** (2026-10-24). 2026-10-20에 제안, 2026-10-24에 MVP 범위로 구현하고 서버 Before/After를 측정했다(아래 "근거"). **Pi 4 실측은 아직 없다**(탐지 속도, 카메라 프레임, 정확도). Pi에서 재면 여기에 덧붙인다.
- 범위: **2026-10-24 MVP로 축소.** 아래 표에서 "MVP 제외"로 표시한 것은 `AI_FINAL_DESIGN.md` 12절의 추후 개선으로 옮겼다. MVP 결정은 같은 문서 10절.
- 바꾸는 결정: 0005의 "장비는 판단하지 않고 1분마다 보낸다" 중 **촬영 시점** 부분. 0004의 규칙 3(비위반 3회 종료)과 규칙 4(사진 10분 끊김 종료)의 **입력**. 0010의 "방법 2(장비가 바뀌었을 때만 전송)는 수백 대일 때 검토"를 앞당긴다.
- 유지하는 결정: 0005의 "판단은 서버가 한다", "사진은 전체를 보낸다". 0004의 "주차 한 번 = 위반 한 건"과 2회 연속 확정. 0006의 재압축 금지.

## 문제

장비는 차가 몇 시간 서 있어도, 밤새 비어 있어도 1분마다 사진을 보내고 서버는 매번 두 모델을 돌린다(0010). 하루 1,440장 중 대부분은 "아까와 같음"을 확인하는 데 쓰인다. 반대로 Pi가 차량이 있을 때만 보내면(리팩터링 이전 코드) 서버가 "차가 나갔다"와 "장비가 꺼졌다"를 구분하지 못해 사건 묶기의 종료 규칙이 동작하지 않는다(0005).

필요한 것은 두 가지다. 사진은 **상황이 바뀔 때** 보내되, 서버는 **장비가 살아 있고 자리가 어떤 상태인지** 계속 알아야 한다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 0010의 방법 1: 서버가 응답에 "다음 사진은 5분 뒤"를 넣는다 | 변경이 가장 작지만, 차가 떠난 것을 최대 5분 뒤에 알고 사진은 여전히 주기적으로 간다 |
| 직전 사진과 픽셀 차이로 변화를 감지 | AI 없이 가능하지만 조명 변화, 사람 통행, 옆 칸 차량에 모두 반응한다 |
| Pi에서 가벼운 YOLO로 **지정 주차면 한 칸**의 점유를 판정하고, 점유 상태가 바뀔 때만 사진을 보낸다. 매분 Heartbeat로 연결과 점유 상태를 알린다 | 채택 |

## 결정

**역할 분리: Pi는 "언제 보낼지"를, 서버는 "위반인지"를 판단한다.** Pi의 판정은 사건을 직접 만들거나 닫지 않는다.

### Pi 4 (장비)

| 항목 | 내용 | 초기값 |
|---|---|---|
| 차량 탐지 모델 | YOLO26s (COCO 사전학습) NCNN, 입력 480px. nano 모델은 sample_c 각도에서 신뢰도가 0.1~0.5로 흔들려 쓸 수 없었다 | 설정 `PG_DETECTOR_MODEL` |
| 주차면 구분 | 4점 사다리꼴 ROI(정규화 좌표). 박스마다 ① 아랫변 중심이 ROI 안 ② 박스∩ROI/박스 면적 ③ 박스 면적/화면 ④ 좌우 끝에 잘린 좁은 박스 제외 ⑤ 신뢰도. 모두 통과한 박스가 하나라도 있으면 그 프레임은 "점유" | ROI는 sample_c 기준. 겹침 진입 0.30 / 이탈 0.15, 면적 5%, 잘림 폭 35%, 신뢰도 0.40 |
| 연속 프레임 | 점유 N프레임 연속이면 진입, 비점유 M프레임 연속이면 출차. 점유의 연속성만 말하고 같은 차임을 증명하지 않는다 | 5초 간격, 진입 3 / 출차 6 |
| 사진을 보내는 때 | `arrived`(진입 확정), `confirm`(서버가 요청했을 때), `refresh`(주차 중 주기 확인), `left`(출차 확정, 빈 자리 사진) | refresh 10분 (설정) |
| Heartbeat | 매분. MVP는 지금 엔드포인트 그대로 서버가 받은 시각만 기록한다. 점유 상태, 마지막 정상 추론 시각, 탐지 프로세스 상태 필드는 MVP 제외 | 60초 |
| 전송 | 하나씩 동기 전송(지금 `pi_client.py` 구조). 실패는 로그만 남기고, 주차 중이면 다음 refresh 때 사진이 다시 간다. 큐, `seq`, `event_id` 는 MVP 제외 | 큐 없음 |
| 전환 | `PG_MODE=event|interval`. interval은 지금의 1분 전송 그대로. 운영에는 쓰지 않고 Before/After 비교·성능 측정용으로만 유지한다 | event (구현 당시 interval 이었으나 2026-10-24 측정 뒤 운영 기본을 event 로 바꿈) |

### 서버

| 항목 | 내용 |
|---|---|
| 요청 필드 | 사진 요청에 선택 필드 `event`(arrived / confirm / refresh / left) 하나를 더한다. 없으면 지금과 같은 1분 전송 사진으로 처리한다 |
| 끊김 판정 | 마지막 **신호**(사진 또는 Heartbeat 중 늦은 것) 기준으로 `EPISODE_GAP_MINUTES`(10분)를 재고, 기존처럼 `SIGNAL_LOST` 로 종료한다. Heartbeat가 오는 동안은 주차 중 사진이 10분마다만 와도 끊김이 아니다. `signal_lost_at` 기록, 복구 시 동기화, 장기 미복구 정리 사유는 MVP 제외 |
| 출차 처리 | `event=left` 사진을 서버가 비위반(`no_vehicle` 또는 `permitted`)으로 확인하면 1회로 바로 종료한다. 종료 사유는 지금과 같다. `left` 가 아닌 사진은 0004의 "비위반 3회 연속" 그대로 |
| 중복과 순서 | MVP 제외. Pi가 하나씩 동기 전송하므로 순서가 뒤바뀌지 않는다 |
| 판정 불가 | MVP 제외. 판정값은 `violation` / `permitted` / `no_vehicle` 셋을 유지하고, 추론 실패는 지금처럼 503을 돌려주고 사건 판정을 건너뛴다(사용자 결정 2026-10-24) |
| 두 번째 확정 사진 | 응답 형식을 바꾸지 않는다. Pi가 `result: violation_pending` 을 보고 60초 뒤 `confirm` 사진을 보낸다. 서버는 일반 사진으로 처리하면 기존 2회 규칙이 그대로 동작한다. 정상 차량은 사진 1장으로 끝난다. 자세한 것은 0004와 `AI_FINAL_DESIGN.md` 5절 |

## 이유

- **서버가 끝까지 판사다.** Pi 판정이 틀려도(옆 칸 차량, 조명) 사건은 서버 사진 판정으로만 생기고 닫힌다. 0005의 취지를 지킨다.
- **Heartbeat가 있어야 "보내지 않음"이 정보가 된다.** 사진이 안 와도 Heartbeat의 `occupied` 로 차가 그대로인지, 장비가 죽었는지 안다.
- **nano가 아니라 small 모델.** 측정값(PC): sample_c의 주차 차량 신뢰도가 yolo26n 0.16~0.32, yolo26s 0.85~0.92, yolo26s NCNN 480 0.93. 5초에 한 프레임이면 Pi 4에서 1초 안쪽이기만 하면 된다(추정).
- **MVP는 최소 변경이다.** 서버에서 바뀌는 곳은 끊김 기준 시각, `left` 즉시 종료, `event` 필드 세 곳이다. 순서·중복·복구는 큐가 없는 동안 문제가 생기지 않으므로 뒤로 미뤘다(사용자 결정 2026-10-24).

## 결과

- 얻을 것(추정): 정상 차량 주차 1회에 사진 1장(arrived) + refresh 몇 장. 빈 자리는 사진 0장. 차량 이탈을 30초 안에 안다.
- 감수할 것: Pi에 모델이 올라간다(NCNN 37MB, 속도 미측정). Pi 코드가 상태 기계가 된다. 서버 사건 묶기는 `event` 필드 유무로 두 방식을 함께 처리한다. `arrived` 전송에 실패하면 다음 refresh(10분)까지 위반을 모른다(MVP에서 감수).
- 측정으로 확인할 것: 하루 사진 수, 전송량, 추론 횟수와 시간, 서버 CPU·메모리, 알림 지연(Before/After), Pi CPU·메모리, 진입·출차 정확도와 지연.
