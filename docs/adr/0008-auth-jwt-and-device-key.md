# 0008. 사용자는 JWT와 Refresh Token, 장비는 장비별 인증 키

- 상태: 결정됨 (2026-10-01)

## 문제

기존 서비스는 Flask 서명 쿠키 세션을 썼고 서명용 Secret이 코드에 적혀 공개 저장소에 올라가 있었다. 장비가 호출하는 API에는 인증이 아예 없어서 기기 번호만 알면 누구나 위반을 등록할 수 있었다. 고객 가입과 기기 등록 API도 열려 있었다.

## 결정: 사용자 인증

- **Access Token**: JWT, 유효 15분. Role과 회사 ID를 담는다. 화면은 메모리에만 보관한다.
- **Refresh Token**: 무작위 문자열. httpOnly 쿠키로 전달하고 DB에는 hash만 저장한다. 쓸 때마다 새 것으로 교체하고 이전 것은 폐기한다.
- 로그아웃하면 Refresh Token을 폐기한다. 비활성화된 관리자나 회사는 다음 요청부터 거부된다.

### 이유

| 대안 | 판단 |
|---|---|
| 기존 쿠키 세션 유지 | 서버가 세션을 강제로 끊을 방법이 없다 |
| 서버 저장 세션 (Redis 등) | 저장소가 하나 더 필요하다 |
| JWT만 쓰고 유효 기간을 길게 | 탈취되면 만료까지 막을 수 없다 |
| 짧은 JWT + DB에 기록한 Refresh Token | 채택. 요청 처리는 DB 조회 없이 서명 검증만 하고, 끊어야 할 때는 Refresh Token을 폐기한다 |

서버가 여러 대로 늘어도 인스턴스 사이에 공유할 세션 상태가 없다.

## 결정: 장비 인증

- 장비마다 인증 키를 하나 발급한다. 키는 등록할 때 한 번만 보여 주고 DB에는 hash만 저장한다.
- 장비는 `X-Device-Key` 헤더로 키를 보낸다.
- 서버는 키로 장비를 찾고, 그 장비가 속한 주차장과 회사를 DB에서 읽는다. 요청에 담긴 소속 정보는 받지 않는다.
- 장비, 주차장, 회사 중 하나라도 비활성이면 거부한다.
- 키가 유출되면 재발급한다. 이전 키는 즉시 무효가 된다.

## 결과

- 얻은 것: 열려 있던 쓰기 API가 모두 인증을 요구한다. 장비가 다른 회사에 데이터를 넣을 수 없다. 키 유출에 대응할 수 있다.
- 감수한 것: 화면에서 Token 갱신 처리가 필요하다. API 호출을 한 모듈에 모아 401이면 한 번 갱신하고 재시도하게 했다.
- 남은 것: Secret은 환경변수에서 읽지만 기본값이 코드에 있다. 운영에서는 반드시 외부에서 주입해야 한다(이후 Secrets Manager). 로그인 시도 제한과 비밀번호 정책은 아직 없다.

## 근거

- `backend/app/auth/security.py`, `backend/app/auth/decorators.py`, `backend/app/api/auth.py`
- 화면: `frontend/src/api/client.js`
- 테스트: 로그인, 갱신, 로그아웃 후 갱신 거부, 키 재발급 후 이전 키 거부
- 실제 확인: 브라우저 출처 기준의 CORS 응답과 쿠키 속성(HttpOnly, SameSite, 경로 제한)

## 한 줄 설명

요청 처리는 짧은 JWT로 상태 없이 하고 끊어야 할 때는 DB에 기록한 Refresh Token을 폐기하며, 장비는 hash로만 저장하는 장비별 키로 인증해 소속을 서버가 결정하도록 했습니다.
