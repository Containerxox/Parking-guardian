# 0015. 번호판 OCR은 서버에서, 확정된 위반 사진에만 돌린다

- **대체됨 (2026-10-25): [0017](0017-remove-plate-ocr.md) "번호판 OCR을 MVP에서 제거한다".** 아래 내용과 측정값은 역사 기록으로 남긴다. 코드(`adapters/ocr.py`)는 삭제됐고 모델은 `C:\parking_guardian\archive\ocr-models\` 에 보관.
- 상태(당시): **결정됨** (2026-10-24). 2026-10-20 제안, 2026-10-24 MVP 범위로 구현(`backend/app/adapters/ocr.py`)하고 샘플 3장으로 확인했다. 3장 중 1장을 높은 신뢰도로 잘못 읽었다(아래 "근거"). Pi 카메라 사진에서는 아직 확인하지 않았다.
- 범위: **2026-10-24 MVP.** 결정 3의 `plate_status` 와 결정 5(OCR 재실행, 보존 기간)는 MVP 제외(`AI_FINAL_DESIGN.md` 12절).
- 바꾸는 결정: 0011 "번호판 OCR은 넣지 않는다"를 대체한다.
- 유지하는 것: 0011의 "OCR은 사건 묶기의 주 기준이 아니라 보조 신호"와 개인정보 최소 수집 원칙. 0004의 시간 기준 사건 묶기.

## 문제

0011은 OCR을 넣지 않기로 했지만 "상습 위반 통계, 신고 시 번호판 확인이 실제 요구가 되면 다시 검토한다"고 남겼다. 사용자가 OCR 도입을 확정했다. 다시 정할 것은 **어느 모델을, 어디서, 어느 사진에** 돌리는가다.

## 검토한 대안

| 항목 | 대안 | 판단 |
|---|---|---|
| 모델 | EasyKoreanLpDetector (gyupro) | 채택. 프로젝트 사진 4장에서 4장 모두 정확히 읽었다 |
| 실행 위치 | Pi / 서버 / 별도 FastAPI 서비스 | **서버의 Flask 프로세스 안 Adapter**. Pi 4는 차량 탐지만으로도 여유가 없고, FastAPI 서비스는 아직 없어 Phase 4에서 분리 효과를 따로 측정한다 |
| 실행 시점 | ① 진입 사진마다 ② 위반 판정 사진마다 ③ 위반이 **확정된** 뒤 | **③**. ①은 정상 차량 번호판까지 매번 읽어 저장하게 되어 0011의 개인정보 우려가 그대로이고 비용이 주차당 1초가 된다 |
| 사건 묶기에 쓰는가 | OCR 불일치로 사건을 나눈다 / 표시만 한다 | **표시만**. 같은 번호판도 사진마다 다르게 읽힌다. 차량 교체의 1차 근거는 Pi의 `left`/`arrived` 이벤트(0014)이고, OCR 불일치는 사건에 "확인 필요"만 남긴다 |

## 결정

1. 모델은 EasyKoreanLpDetector. 파이프라인은 차량 탐지(YOLO26s, COCO) → 번호판 탐지(`lp_det.pt`, YOLOv5) → EasyOCR 커스텀 인식기(`best_acc.pth`). 세 파일을 `backend/models/` 아래에 두고 Git에는 올리지 않는다(기존 모델과 같은 규칙).
2. `backend/app/adapters/ocr.py` 에 Adapter를 추가한다(0007 구조). 테스트용 Mock을 함께 둔다.
3. 위반이 **확정된** 사진(두 번째 위반 판정 사진)에만 돌린다. 결과는 위반 기록에 `plate_number`, `plate_confidence` 두 컬럼으로 붙인다. 못 읽으면 둘 다 비워 둔다. `plate_status` 컬럼은 MVP 제외.
4. OCR 실패는 위반 저장과 알림에 영향을 주지 않는다. 사진 저장 실패, 알림 실패와 같은 방식으로 이력만 남긴다.
5. (MVP 제외) 주차 중 `refresh` 사진이 위반 판정일 때 OCR을 다시 돌려 비교하는 것, "확인 필요" 표시, 번호판 보존 기간과 조회 권한은 MVP 뒤 별도 단계에서 정한다. MVP에서는 위반 확정 때 1회만 돌린다.
6. `OCR_ENABLED` 설정이 꺼진 상태가 기본이다(테스트, 모델 파일이 없는 환경). 켜면 Flask 프로세스에 모델을 올린다.

## 이유

- **검증된 모델이다.** 4장 결과: 138버5401 (0.979), 50로0482 (1.000), 153부2726 (0.840), 위반 사진의 50로0482 (1.000). PC CPU에서 사진 1장 약 0.8~1.2초, 세 모델 로딩 뒤 메모리 +490MB, 첫 로딩 약 15초.
- **실패 양상을 알고 있다.** 배경의 작은 번호판(71px)은 신뢰도 0.27~0.31로 잘못 읽었다. 신뢰도 기준과 "가장 큰 차량의 번호판만" 규칙이 필요하다. 같은 차가 truck과 car로 두 번 잡히고 번호판 class가 두 개라 중복 박스가 나온다.
- **확정 뒤에만 돌리면** 하루 OCR 횟수가 위반 건수와 같아진다. 정상 차량의 번호판은 저장되지 않는다.

## 결과

- 얻을 것: 위반 기록에 번호판이 붙어 신고와 상습 차량 확인이 가능해진다.
- 감수할 것: 서버 메모리 +490MB(추정, PC 측정값), 위반당 추론 약 1초 추가. 번호판은 검색 가능한 개인정보라 보존 기간과 접근 권한을 정해야 한다(MVP 뒤 별도 단계). Windows에서는 기존 모델과 같은 PosixPath 우회가 필요하다.
- 사건 묶기 규칙은 OCR과 무관하게 그대로 동작한다. 0011이 요구한 "못 읽어도 시간 기준 규칙이 동작한다"를 지킨다.

## 근거

**MVP 구현 확인 (2026-10-24, 이 PC).** 모델 로딩 25.7초, RSS +428 MB. 사진 1장 0.5~1.3초. sample_a `138버5401`(0.90, 정확), sample_b `50로0482`(0.77, 정확), sample_c **`153보2726`(0.95, 틀림. 실제 `153부2726`)**. MVP 구현은 원본 파이프라인의 차량 탐지(YOLO26s) 단계를 빼고 사진 전체에서 가장 큰 번호판을 읽는데, 2026-10-20 검증(차량 crop 포함)에서는 같은 사진을 `153부2726` 0.84 로 맞게 읽었다. 전처리를 바꿔도 같은 오독이 나왔고 원인은 확인하지 못했다. 신뢰도 기준(0.5)으로는 걸러지지 않으므로 **번호판은 관리자가 사진으로 확인하는 보조 정보**이고, 차량 crop 단계 복원은 `AI_FINAL_DESIGN.md` 12절(추후 개선)에 넣었다. 상세는 `docs/measurements/README.md` "OCR 비용".

구현: `OCR_ENABLED`(기본 false), `Violation.plate_number` / `plate_confidence`(마이그레이션 `a3c7e51d9b02`), `device.py` 에서 사진 저장 뒤·알림 전에 한 번 실행, 실패와 미인식은 `OCR_FAILED` 이력. 테스트 6개(`tests/test_ocr.py`). 모델 파일은 `backend/models/lp_det.pt`, `backend/models/lp_models/`(Git 제외). `easyocr` 를 `requirements.txt` 에 추가했다.

## 한 줄 설명

OCR을 넣지 않기로 했던 결정을 뒤집되, 정상 차량의 번호판은 읽지 않도록 확정된 위반 사진에만 서버 Adapter로 돌리고, 사건 묶기의 근거가 아니라 위반 기록의 보조 정보로만 쓰기로 했습니다.
