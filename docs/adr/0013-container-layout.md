# 0013. 컨테이너 구성: 화면과 API는 한 주소로, 모델 파일은 이미지 밖에 둔다

- 상태: 결정됨 (2026-10-02)

## 문제

지금까지 실행하려면 Python 가상환경, torch, YOLOv5 소스, Node.js를 PC에 직접 설치하고 터미널 두 개에서 Backend와 Frontend를 따로 띄워야 했다. 다른 PC나 클라우드에서 같은 상태를 다시 만들 방법이 없었다.

`docker compose up` 한 번으로 DB, Backend, Frontend가 모두 뜨게 만들면서 네 가지를 정해야 했다.

1. 브라우저가 화면과 API를 어떻게 찾아가는가
2. 412MB짜리 모델 파일을 어디에 두는가
3. DB 마이그레이션을 언제 실행하는가
4. 운영용 서버(gunicorn)를 몇 개의 프로세스로 띄우는가

## 검토한 대안

| 질문 | 대안 | 버린 이유 |
|---|---|---|
| 화면과 API 주소 | 화면은 8080, API는 5000으로 따로 열고 CORS로 허용 | 빌드할 때 API 주소를 박아야 해서 환경마다 이미지를 다시 만들어야 한다. Refresh 쿠키가 다른 출처로 가야 해서 HTTPS 환경에서 설정이 까다로워진다 |
| 모델 파일 | 이미지 안에 포함 | 이미지가 400MB 더 커지고, 모델을 바꿀 때마다 이미지를 다시 빌드한다. 모델은 Git에도 없다 |
| 마이그레이션 | 사람이 `flask db upgrade` 를 직접 실행 | "한 번에 실행"이 깨진다. 빠뜨리면 서버가 뜬 뒤에 오류가 난다 |
| gunicorn 프로세스 수 | CPU 수만큼 worker | worker마다 모델을 따로 올려서 메모리가 worker 수만큼 든다 |

## 결정

| 질문 | 결정 |
|---|---|
| 화면과 API 주소 | Frontend 컨테이너의 nginx가 화면 파일을 주고, `/api/` 로 시작하는 요청은 Backend로 넘긴다. 브라우저는 주소 하나(`http://127.0.0.1:8080`)만 안다. 화면 코드의 API 주소는 `/api/v1` (상대 경로)다 |
| 모델 파일 | 이미지에 넣지 않고 실행할 때 `backend/models` 폴더를 읽기 전용으로 연결한다. YOLOv5 소스(3.8MB)는 이미지에 넣는다 |
| 마이그레이션 | Backend 컨테이너가 시작할 때 `flask db upgrade` 를 먼저 실행하고 서버를 띄운다. 로컬 Compose에서는 데모 데이터도 함께 넣는다(`SEED_DEMO_DATA=1`) |
| gunicorn | worker 1개, thread 4개. 환경변수로 바꿀 수 있다 |

그 밖에 두 컨테이너 모두 root가 아닌 일반 사용자로 실행한다. 위반 사진은 Docker volume(`backend_storage`)에 저장한다.

## 이유

- **한 주소.** 건물 안내 데스크와 같다. 방문자는 정문 하나로 들어오고, 데스크가 용건에 따라 화면 창구와 API 창구로 안내한다. 같은 이미지를 로컬, 테스트, 운영에 그대로 쓸 수 있고 CORS 설정이 필요 없다. 나중에 AWS의 ALB가 경로에 따라 나눠 주는 구조와도 같다.
- **모델은 이미지 밖.** 코드와 모델은 바뀌는 주기가 다르다. 이후 단계에서 모델을 S3에 두고 내려받는 방식으로 갈 때도 "밖에서 받아 온다"는 구조가 그대로 이어진다.
- **시작할 때 마이그레이션.** 지금은 Backend가 한 대라서 가장 단순한 방법이 안전하다.
- **worker 1개.** 스티커 모델만 370MB다. AI 추론은 이미 잠금으로 한 번에 한 장씩 처리하므로 worker를 늘려도 얻는 것이 적다. 추론이 별도 서비스로 나간 뒤에 다시 정한다.

## 결과

- 얻은 것: `docker compose up -d --build` 한 번으로 전체가 뜬다. PC에 Python, Node.js, torch를 설치하지 않아도 된다.
- 감수한 것:
  - Backend 이미지가 2.83GB다. torch와 YOLOv5 의존성 때문이다. AI 추론을 별도 서비스로 분리하면 Backend 이미지는 수백 MB로 줄어든다.
  - 컨테이너를 새로 띄운 뒤 첫 사진은 모델을 읽느라 약 34초 걸린다(로컬 실행은 약 16초). 그다음부터는 약 1초다.
  - Backend를 다시 만드는 약 12초 동안 화면의 API 요청은 502를 받는다. nginx를 다시 띄우지 않아도 스스로 복구된다.
- 나중에 바꿀 것:
  - Backend가 여러 대가 되면 시작할 때마다 마이그레이션을 동시에 실행하게 된다. 그때는 마이그레이션을 배포 전에 한 번만 도는 작업으로 뺀다.
  - HTTPS 뒤에 놓이면 Backend가 만드는 사진 주소가 `http://` 로 나온다. 프록시가 알려 주는 원래 주소(`X-Forwarded-Proto`)를 믿도록 설정해야 한다. AWS 단계에서 한다.
  - nginx 설정의 DNS 주소(`127.0.0.11`)는 Docker 전용이다. AWS에서는 화면 제공 방식 자체를 다시 정한다.

## 근거

- 설정: `docker-compose.yml`, `backend/Dockerfile`, `frontend/Dockerfile`, `frontend/nginx.conf`
- 확인한 것 (2026-10-02, 실제 모델 사용, 모두 8080 주소를 거쳐서 확인):
  - 화면 파일 제공, 화면 내부 경로(`/violations/123`)로 바로 들어와도 화면이 뜸
  - 로그인, Refresh 쿠키 발급과 재발급
  - `sample_b` 3회 업로드 → 확인 중 → 위반 확정 → 계속 주차 중. 담당 관리자에게 알림 1건
  - `sample_c`(4MB) 업로드 통과. nginx 기본 제한은 1MB라서 16MB로 올려 두었다
  - 판정 수치가 로컬 실행과 같음: `sample_a` 스티커 0.64, `sample_c` 스티커 0.92, `sample_b` 스티커 없음
  - 저장된 사진이 올린 파일과 1바이트도 다르지 않음(재압축 없음)
  - 다른 회사 계정은 그 위반을 404로 받음
  - Backend 컨테이너를 새로 만들어도 사진이 남아 있고, nginx가 새 컨테이너를 찾아감
  - 종료 신호 후 3초 안에 정상 종료
  - 테스트 31개: SQLite, PostgreSQL 모두 통과
- 확인하지 못한 것: 브라우저에서의 실제 화면

## 한 줄 설명

nginx가 화면과 API를 한 주소로 묶어 같은 이미지를 어느 환경에서나 쓰게 했고, 자주 바뀌지 않는 큰 모델 파일은 이미지에 넣지 않고 실행할 때 연결했습니다.
