# 0017. 번호판 OCR을 MVP에서 제거한다

- 상태: **결정됨** (2026-10-25, 사용자 결정). 코드 제거와 전후 측정 완료.
- 바꾸는 결정: **0015 "번호판 OCR은 서버에서, 확정된 위반 사진에만 돌린다"를 대체한다.** 0011 "번호판 OCR은 넣지 않는다"의 결론으로 돌아간다. 두 문서가 어긋나 보이면 이 문서를 따른다.
- 유지하는 것: `violations.plate_number`, `plate_confidence` 컬럼과 마이그레이션 `a3c7e51d9b02`(스키마 변경 없음), `HistoryAction.OCR_FAILED` 와 화면 라벨(과거 이력 호환).

## 문제

OCR 은 2026-10-24 에 MVP 범위로 구현됐다(0015). 확정된 위반 사진 1장에서 번호판을 읽어 상세 화면에 보여 주는 보조 정보였다. AWS 구축을 시작하면서 다시 보니:

- 핵심 기능(점유 감지 → 스티커 판정 → 위반 사건 → 알림 → 처리)에 OCR 은 필수가 아니다. 관리자는 사진으로 차량을 확인한다.
- 샘플 3장 중 1장을 **높은 신뢰도(0.95)로 잘못** 읽었다(`153부2726` → `153보2726`). 보여 주면 오히려 오해를 만든다. 개선은 우선순위가 아니었다.
- 비용이 있다. `easyocr` 과 전용 의존성 10개, 모델 37.6 MB, 켜면 메모리 +428 MB 와 첫 로딩 26초, 그리고 Phase 2 에서 추론 서비스로 옮겨야 하는 코드.
- AWS 로 가면 OCR 모델도 S3 모델 버킷에 올리고 initContainer 가 받아야 한다. 안 쓰는 것을 운반하는 셈이다.

## 검토한 대안

| 대안 | 버린 이유 |
|---|---|
| 그대로 두고 `OCR_ENABLED=false` 로 운영 | 코드·의존성·모델이 남아 이미지와 설계 문서가 복잡하다. "꺼진 기능"을 Phase 2 에서 또 옮겨야 한다 |
| 컬럼까지 지우는 마이그레이션 추가 | 개발 DB 에 이미 적용된 마이그레이션을 되돌리는 변경이 하나 더 생긴다. NULL 컬럼 두 개가 남는 비용은 0 에 가깝다. 사용자 조건: 불필요한 스키마 변경 금지 |
| 모델 파일 삭제 | 되돌릴 수 없다. 리포 밖에 보관하면 비용이 없다 |

## 이유

핵심 기능이 아니고, 정확도가 보여 줄 수준이 아니며, 클라우드 단계마다 운반 비용이 붙는다. 세 가지가 겹치면 빼는 쪽이 맞다. 되돌리기는 Git(`09d0ef3` 도입 커밋)과 보관 폴더로 가능하다.

## 결과

**전후 비교 (2026-10-25, 이 PC, `docker compose`, 같은 사진 sample_e)**

| 항목 | 제거 전 (10-24 빌드) | 제거 후 | 차이 |
|---|---|---|---|
| Backend 이미지 | 3.16 GB | **2.84 GB** | −320 MB (−10%) |
| `requirements.txt` 레이어 | 308 MB | 77 MB | −231 MB |
| 설치 패키지 수 | 76 | 66 | −10 (`easyocr`, `scikit-image`, `imageio`, `tifffile`, `lazy-loader`, `shapely`, `pyclipper`, `python-bidi`, `ninja`, `opencv-python-headless`) |
| 컨테이너 유휴 메모리 | 81 MiB | 81 MiB | 같음 |
| 첫 사진 뒤 메모리 | 892 MiB | 890 MiB | 같음 |
| 첫 사진 응답(모델 로딩 포함) | 18.2초 | 12.7초 | 측정 편차로 본다(아래) |
| 둘째 사진 응답 | 2.4초 | 1.7초 | 같은 이유 |
| 테스트 | 43개 | 37개(OCR 6개 삭제) → 이후 46개(S3·설정 추가) | |

- 이미지 레이어 차이(231 MB)와 이미지 전체 차이(320 MB)가 다른 것은 레이어 압축·공유 계산 방식 때문으로 보이며 따로 확인하지 않았다.
- **메모리가 같은 이유**: OCR 은 `read()` 가 처음 불릴 때 `easyocr` 을 import 하는 지연 로딩이었고 `OCR_ENABLED=false` 로 운영했다. 그래서 실행 중 메모리는 원래 OCR 영향이 없었다. 실질 효과는 "켰을 때 +428 MB(측정값)" 선택지가 사라진 것이다.
- **첫 사진 시간 차이(18.2 → 12.7초)는 OCR 제거 효과가 아니다.** 모델 로딩은 앞유리·스티커 모델만 하며 바뀐 것이 없다. 디스크 캐시와 PC 상태에 따른 편차로 본다. 각 1회 측정이라 통계적 의미는 없다.
- 회귀 확인: `sample_b` 2장 → 위반 8 생성(`NOTIFIED`, 사진 `UPLOADED`, `plate_number` NULL), 담당 관리자 2명 × 2채널 알림 `SENT`, 이력 `DETECTED` → `NOTIFIED`.

얻은 것: 이미지 10% 감소, 코드 약 450줄과 의존성 10개 감소, Phase 2 에서 옮길 것이 하나 줄었다. S3 모델 버킷은 2개 파일(412 MB)만 받는다.

감수한 것: 번호판 정보가 화면에서 사라졌다. 다시 넣으려면 Phase 2 의 추론 서비스에 별도 모델로 붙이는 것이 맞고, 그때는 차량 crop 단계가 있는 원본 파이프라인(0015 근거의 2026-10-20 검증)으로 정확도를 먼저 확인한다.
