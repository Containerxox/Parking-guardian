# 0010. 촬영 주기 최적화는 측정한 뒤에 적용한다

- 상태: 결정됨 (2026-10-02). 구현은 클라우드 단계에서 한다

## 문제

장비는 차량이 계속 서 있어도 1분마다 사진을 보내고 서버는 매번 AI로 판정한다. 위반 차량뿐 아니라 정상 차량이 몇 시간 주차 중일 때도, 밤새 자리가 비어 있을 때도 같다. 대부분의 사진은 "아까와 같음"을 확인하는 데 쓰인다.

부담은 DB가 아니라 추론에 있다. 사건이 진행 중일 때 DB에서 바뀌는 것은 한 row의 시각뿐이다.

| 항목 | 장비 1대 기준 (로컬 CPU 측정) |
|---|---|
| 사진 한 장 판정 | 약 0.6초 |
| 하루 사진 수 | 1,440장 |
| 하루 추론 시간 | 약 14분 |
| 장비 100대일 때 | 1초에 1.7장. 추론 프로세스 하나로는 밀리기 시작한다 |

## 검토한 방법

| 방법 | 내용 | 비용 |
|---|---|---|
| 1. 서버가 촬영 간격을 지시 | 차량이 계속 있는 것이 확인되면 서버가 응답에 "다음 사진은 5분 뒤"를 넣는다. 상황이 바뀌면 1분으로 돌아온다 | 변경이 작다. 차량 이탈을 알아채는 시간이 최대 5분 늦어진다 |
| 2. 장비가 화면이 바뀌었을 때만 전송 | Pi에서 직전 사진과 비교한다. AI 없이 가능하다 | 효과가 가장 크다. 밝기 변화 처리 등 장비 코드가 복잡해진다 |
| 3. 추론 서버를 늘린다 | 추론 서비스를 분리하고 부하에 따라 대수를 늘린다 | 돈이 든다 |

## 결정

**지금은 1분 고정으로 둔다.** 클라우드 환경에서 아래 순서로 진행하고 각 단계의 수치를 비교한다.

1. **기준 측정.** 지금 구조 그대로 부하를 걸어 장비 몇 대에서 응답이 밀리는지 본다.
2. **방법 1 적용 후 측정.** 같은 조건에서 요청 수와 추론 서버 사용률이 얼마나 줄었는지 본다.
3. **방법 3 적용 후 측정.** 남은 부하를 서버를 늘려 감당하는지, 몇 대가 필요한지 본다.

## 이유

- **지금 적용하면 효과를 보여 줄 수 없다.** 적용 전 수치가 같은 환경에 있어야 비교가 된다. 로컬에서 잰 값은 환경이 달라 비교 대상이 못 된다.
- **요청 줄이기를 서버 늘리기보다 먼저 한다.** 요청을 줄이는 것은 돈이 들지 않고 서버를 늘리는 것은 돈이 든다.
- 지금 규모(장비 몇 대)에서는 문제가 없다.

## 구현할 때 지킬 것

- 방법 1은 설정값 하나로 켜고 끌 수 있게 만든다. 같은 서버에서 켠 상태와 끈 상태를 바로 비교하기 위함이다.
- 부하 도구는 실제 장비처럼 행동해야 한다. 일정하게 요청을 쏘는 도구로는 방법 1의 효과가 보이지 않는다. 가상 장비가 "빈 자리, 차량 주차, 차량 이탈"을 흉내 내고 서버가 알려 준 간격대로 보내야 한다. `device/pi_client.py` 의 전송 부분을 재사용한다.

촬영 간격 규칙:

| 서버가 본 상황 | 다음 촬영까지 |
|---|---|
| 빈 자리, 위반 확인 중 | 1분 |
| 위반 차량 또는 정상 차량이 계속 주차 중 | 5분 |
| 차량이 안 보이기 시작함 | 1분으로 복귀 |

비교할 수치: 분당 요청 수, 추론 서버 CPU 사용률, 응답 시간(p95), 서버 한 대로 감당 가능한 장비 수, 필요한 서버 대수와 비용.

## 결과

- 얻은 것: "측정으로 문제를 드러내고, 싼 방법부터 적용하고, 수치로 효과를 보인다"는 순서가 생긴다.
- 감수한 것: 그때까지 불필요한 추론이 계속 돈다.
- 방법 2는 장비가 수백 대로 늘 때 검토한다.

## 한 줄 설명

불필요한 추론을 줄이는 방법을 알고 있었지만 적용 전 수치 없이는 효과를 증명할 수 없어서, 클라우드에서 기준을 먼저 측정하고 요청 줄이기, 서버 증설 순서로 적용하기로 했습니다.
