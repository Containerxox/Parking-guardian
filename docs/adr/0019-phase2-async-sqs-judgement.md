# 0019. 사진 접수와 AI 판별을 S3 + SQS FIFO 로 나누고, 상태 이벤트는 큐를 거치지 않는다

## 문제

Phase 1 에서도 장비 요청은 판정이 끝날 때까지 연결과 API 스레드를 잡는다. 판정 용량을 넘는 사진은 거절되고 장비에는 재시도가 없다. 판정 용량은 사진이 오는 순간에 이미 떠 있어야 한다. (거절·유실의 실제 크기는 Phase 1 측정으로 확인한다.)

비동기로 바꾸면 코드에서 확인한 두 가지가 깨진다.

- `record_verdict()` 는 끊김 판정과 `last_seen_at` 에 처리 시각(`utcnow()`)을 쓴다. 큐 지연이 생기면 정상 장비가 SIGNAL_LOST 로 닫힐 수 있다.
- 장비는 응답의 `violation_pending` 을 보고 60초 뒤 confirm 을 찍는다. 응답에 판정이 없으면 이 경로가 끊긴다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| SQS Standard + DB 가드만 | 순서 보장이 없어 모든 순서 문제를 DB 가드가 떠안는다 |
| **SQS FIFO(그룹 = 장비) + DB 순서 가드** | 채택. 장비별 순서는 큐가, 재전달·redrive 로 섞이는 경우는 가드가 막는다 |
| 그룹 = 회사 / 주차장 | 무관한 장비끼리 서로를 막는다. 독 메시지 하나가 회사·주차장 전체를 멈춘다 |
| 그룹 = 주차면 | 사건 상태는 Machine 행에 있다. 한 장비가 여러 면을 보면 두 그룹이 같은 행을 고친다 |
| confirm: 장비 폴링 / 진입 뒤 항상 confirm | 요청 증가 / 정상 차량도 사진 2장 |
| **confirm: Heartbeat 응답의 명령** | 채택 |

## 결정

1. **두 경로.** 상태 경로(Heartbeat, 세션 시작, 출차 보고, 명령 확인)는 API 가 DB 에 바로 반영한다. 판별 경로(모든 사진의 위반 판별)만 큐를 탄다. `left` 요청은 상태 부분이 즉시 반영되어 AI 적체에 막히지 않고, 사건 종료는 빈 자리 판정이 확인할 때 한다.
2. **접수 순서**: S3 `inbox/`(event_id 로 정해지는 키) → DB `detection_jobs` 행(아웃박스) commit → SQS SendMessage → 202. 전송이 실패해도 202 를 주고 재전송기가 보낸다.
3. **재전송기(outbox-relay)**: `pending_publish` 작업을 장비별 seq 순서로 전송(지수 백오프, 포기하지 않음), DLQ 메시지를 DB `dead_lettered` 로 옮김, 끊긴 부수 효과 마무리, 보존 기간 정리. DB 가 진실의 원천이고 SQS 는 운반 수단이다.
4. **식별자**: `event_id`(중복 제거, `UNIQUE(machine_id, event_id)`), `session_id`(진입 ~ 출차), `seq`(세션 안 순서), `command_id`, `job_id`(SQS 중복 제거 ID). 장비 시계(`detected_at`)는 순서 판단에 쓰지 않는다.
5. **순서 가드**: Machine 행에 `current_session_id`, `last_applied_seq`. 현재 세션의 더 큰 seq 만 사건 상태를 바꾸고, 나머지는 판정만 기록하는 `stale`. `left` 판별은 현재 세션의 사건만 닫는다.
6. **시각**: `record_verdict(observed_at=접수 시각)`. 끊김 판정은 상태 경로의 마지막 신호 시각으로 한다.
7. **Worker**: 조건부 UPDATE 로 선점(`claim_attempt` fencing), 추론은 트랜잭션 밖, 판정 결과·사건 반영·작업 `done` 은 한 트랜잭션. 증거 사진 복사와 알림은 commit 뒤 멱등 부수 효과(`effects_status`). 락 유지, 동시 처리 1.
8. **confirm**: Worker 가 `device_commands` 에 `capture_confirm`(`due_at` = 접수 + 60초, `expires_at` = due + 9분)을 만든다. Heartbeat 응답이 명령을 싣고, 장비는 max(due_at, 받은 시각)에 찍는다. 장비는 실행한 command_id 를 기록해 중복 실행하지 않는다.
9. **장비**: 로컬 아웃박스(디스크), seq 순서 전송, full jitter 지수 백오프(최대 60초, `Retry-After` 존중), 이벤트별 포기 기준(refresh·confirm 10분, arrived·left 30분), 202·200(중복) 모두 성공.
10. **보존**: 판별용 임시 사진 `inbox/` 7일, 확정 증거 `violations/` 90일(지금은 기록만 하는 `IMAGE_RETENTION_DAYS` 를 수명 주기로 실제 적용), 작업 행 30일, DLQ 4일.
11. **확장**: KEDA SQS 스케일러, min 1(모델 로딩 때문에 0 은 쓰지 않음). 노드는 Phase 1 과 같은 공용 노드 그룹 3대이고 Worker·API 공존을 허용한다. max 는 노드 수가 아니라 노드별 CPU 요청 여유로 정한다. Phase 1 과의 공식 비교는 같은 노드 사양·수·요청값·시나리오로 한다.

## 이유

- 큐가 순서를, DB 가 진실을 맡으면 각 실패 지점의 복구가 "다시 보내기" 와 "다시 처리해도 같은 결과" 두 가지로 줄어든다.
- 상태와 판별을 나누면 AI 장애 동안에도 장비 연결 상태와 출차 보고가 정확하다.
- 타이밍 분석(설계 문서 6.9): confirm 시각을 서버가 `due_at` 으로 정해 주면 큐 대기 + 추론 시간 q ≤ 60초일 때 늦음은 최대 q 다. Heartbeat 1분 주기를 바꾸지 않아도 된다. 2회 확정은 refresh 사진도 세므로 confirm 이 끝내 안 와도 판정은 10분 안에 이어진다.

## 결과

- 얻을 것(예상, 측정 전): 접수 지연이 판별 용량과 분리된다. 과부하에서 사진이 거절 대신 적체된다. Worker 장애 동안 관리자 API 와 장비 상태가 정상이다.
- 감수할 것: 테이블 4개(작업, 판정 결과, 세션, 명령), 재전송기, 상태 기계, redrive 운영 절차, 장비 프로토콜 변경. LED·confirm 이 Heartbeat 한 주기 늦을 수 있다. **End-to-End 판별 지연은 동기보다 늘 수 있다.** 비교 표의 1행은 접수 응답이 아니라 End-to-End 지연과 유실 수다.
- 비용(추정): SQS 는 무료 범위 안. SQS VPC Endpoint 는 월 십수 달러대라 쓰지 않고 NAT 를 경유한다.

- 2026-11-02 (사용자 승인): `detection_results.violation_id` 는 "그 판정이 반영된 위반 사건" 을 뜻한다(그 작업이 만든 위반만이 아님). 위반이 확정되는 트랜잭션에서 그 사건의 선행 판정(확정 전에 반영되어 확정 횟수에 들어간 위반 판정)을 연결하고, 이후 같은 사건에 실제 반영된 판정(refresh 등)도 반영 트랜잭션에서 연결한다. stale 판정, 무관한 세션·이벤트, 다른 위반 사건의 판정은 연결하지 않는다. 세션이 같다는 이유만으로 일괄 연결하지 않고, 그 사건에 속한다는 근거(사건 진행 상태에 실제로 반영되었는지)로 연결한다. `detection_jobs.violation_id` 는 그대로 "이 작업이 만든 위반" 이다. 구현과 테스트는 5단계(Worker).
- 2026-11-02 (사용자 승인, 3단계 분석): 결정 6 의 "끊김 판정은 상태 경로의 마지막 신호 시각으로 한다" 를 다음으로 구체화한다. 접수 API 가 장비 행을 잠근 채 **직전 신호 시각**(마지막 사진·Heartbeat 중 늦은 것)을 작업 행 `detection_jobs.prev_signal_at` 에 저장하고 그다음 마지막 신호 시각을 갱신한다. Worker 는 `record_verdict(observed_at=received_at, previous_signal_at=prev_signal_at)` 로 판정한다. 이유: 접수가 신호 시각을 먼저 갱신하면 Worker 가 볼 때 직전 신호가 그 사진 자신이 되어 끊김을 영영 감지하지 못한다. 10분 규칙·종료 시각(마지막 목격)·횟수 초기화와 Phase 1 동기 경로는 그대로다. 감수: 끊김 공백을 가진 작업이 역순 처리·stale 로 반영되지 않으면 SIGNAL_LOST 가 누락될 수 있다(재전송·재부팅 같은 드문 경우). 5단계에서 검증한다. 검토한 대안: 접수 단계에서 직접 판정(이미 큐에 있는 공백 이전 사진이 새 횟수에 섞임), 시간순 신호 기록 테이블(Heartbeat 마다 행 추가).
- 2026-11-02 (사용자 승인): 본문을 읽을 수 없는 큐 메시지(잘못된 JSON, job_id 누락 등)는 판정하지 않고 **삭제하지 않으며 DLQ 로 격리**한다. 오류 원인과 메시지 식별 정보(메시지 ID, 그룹, 수신 횟수)만 기록하고 본문 전체는 기록하지 않는다. 가능하면 SQS redrive 정책(maxReceiveCount)으로 DLQ 에 보내고, 명시적으로 DLQ 에 보낼 때는 전송 성공을 확인한 뒤 원본을 삭제한다. 구현은 5단계.
- 2026-11-02 (사용자 승인, 4단계 확인): 접수 경로 `POST /device/detection-jobs`, 큐가 없으면 404. 409 `event_id_conflict`·`session_conflict` 는 장비가 재시도하지 않는다(설계 6.10). `zone_name` 은 받지 않고 장비에 매핑된 주차면을 쓴다. inbox 키의 날짜 부분은 재검토 중(아직 바꾸지 않음).
- 2026-11-02 (사용자 승인, 5단계 착수 전 충돌 분석): **순서 가드 상태(`machines.current_session_id`, `last_applied_seq`)는 Worker 만 바꾼다.** 접수 API 는 세션 등록(`first_received_at`), 이전 세션 `superseded`·명령 취소, `left` 의 세션 `ended` 만 한다. 이유: 접수 시점에 현재 세션을 바꾸면 큐에 남은 이전 세션 작업이 모두 stale 이 되어 위반 한 건이 통째로 사라졌다(시뮬레이션으로 확인). | A. DB 고유 제약: 작업에 `command_id` 를 저장하고 `UNIQUE(machine_id, command_id) WHERE command_id IS NOT NULL` | 명령 하나 = confirm 작업 최대 하나 | 컬럼 1 + 부분 고유 인덱스 1 (새 마이그레이션) | 막음 | 막음 | **막음** | 명령 상태와 무관해서 가장 강하다. 접수는 이미 장비 행 잠금 안에서 직렬화되므로 경합도 같은 결과이고, 인덱스는 마지막 방어선이다. 두 번째는 200 으로 응답(장비는 성공으로 처리) |

**추천: A** (작업에 `command_id` 저장 + 부분 고유 인덱스). 이유는 명령 상태(fulfilled·cancelled·expired)나 명령 행의 수명(30일)에 의존하지 않고 "한 명령 = confirm 작업 하나" 를 DB 가 보장하며, 접수의 장비 행 잠금과 합쳐져 동시 요청에도 결과가 같고, Worker·재전송기·Heartbeat 를 바꾸지 않는다는 점이다. 기존 `fulfilled` UPDATE 는 그대로 둔다.

**변경 범위 (A)**: ① 새 마이그레이션(`detection_jobs.command_id` UUID NULL + 부분 고유 인덱스, SQLite·PostgreSQL 양쪽, 기존 마이그레이션 수정 없음, Phase 1 데이터 불변) ② 접수: 작업에 `command_id` 저장, 저장소 쓰기 **전에** (장비 행 잠금 전) 같은 `(machine, command_id)` 의 작업이 있는지 확인해 이미 있으면 사진을 저장하지 않고 200(`duplicate: true`, 기존 `job_id`, 이유 `command_already_confirmed`) — 잠금 안에서 다시 확인하고 `IntegrityError` 도 같은 응답으로 바꾼다 ③ `_as_duplicate`: 같은 `event_id` 인데 `command_id` 가 다르면 `event_id_conflict`(409) ④ API.md ⑤ Worker·재전송기·Heartbeat·장비 코드 변경 없음(장비는 200 을 이미 성공으로 처리). Phase 1 `/device/detections` 는 `command_id` 가 없어 영향 없음.

**알려진 한계 (A 도)**: 첫 사진의 작업이 `rejected`·`dead_lettered` 가 되면 그 명령의 confirm 판정은 없다(두 번째 사진도 막힌다). 설계 6.9 대로 confirm 은 정확성이 아니라 지연을 줄이는 장치이고 refresh(10분)가 두 번째 목격을 대신한다. 두 번째 사진이 버려져도 장비의 `seq` 는 하나 비지만 순서 가드는 빈 순번을 허용한다.

**테스트 설계 (구현 전에 먼저 쓸 것)**
1. T1 같은 command_id·다른 event_id 2장: 202 와 200(`command_already_confirmed`), 작업 1개, inbox 객체 1개(두 번째는 저장 전에 걸러짐), 같은 job_id.
2. T2·T3·T4 위 V2·V3·V4 와 같은 순서: 명령이 `fulfilled`·`cancelled`·`expired` 여도 두 번째는 200. Worker 처리 뒤 `detection_count` 가 정확히 2, 결과 2개, 적용 2개.
3. T5 순서 뒤집힘(늦은 첫 사진): 먼저 도착한 쪽이 이기고 나머지는 200. 위반 확정이 한 번.
4. T6 다른 장비가 같은 `command_id`: 둘 다 202(고유 제약은 장비별). `command_id` 없는 confirm·refresh 는 영향 없음.
5. T7 같은 `event_id` 재전송은 지금처럼 200(`duplicate: true`), `event_id` 는 같고 `command_id` 가 다르면 409 `event_id_conflict`.
6. T8 PostgreSQL 동시성: 같은 command_id 요청 둘을 동시에 → 202 하나와 200 하나, 작업 1개, 반복 20회. 고유 인덱스가 실제로 만들어졌는지(`pg_indexes`)와 장비 행 잠금 없이 직접 INSERT 두 번이 `IntegrityError` 인지(마지막 방어선).
7. T9 장치 통합: `executed.json` 을 지운 뒤 Outbox 에 첫 confirm 이 남아 있는 상태에서 명령이 다시 와 두 번째가 찍혀도, 망이 돌아오면 서버에는 작업 1개, 위반 `detection_count` 2 (`test_async_device_integration.py` 에 추가).
8. T10 마이그레이션: 업그레이드·다운그레이드·재업그레이드에서 Phase 1 테이블 불변, 기존 작업은 `command_id` NULL, 부분 인덱스가 NULL 을 여러 개 허용(SQLite·PostgreSQL), 스키마와 모델이 일치.
9. T11 회귀: Phase 1 동기 경로, 정상 confirm 이 `fulfilled`, 8단계 서버 연동 시나리오 4개 그대로 통과.

**구현 결과**: 위 테스트 설계 T1~T11 을 모두 자동 테스트로 구현했다(`tests/test_command_dedupe.py`, `test_command_link_migration.py`, `test_phase2_schema.py`, 장치 통합 T9 는 `test_async_device_integration.py`). 같은 코드를 일부러 깨 보는 변형 검사도 했고(early 확인 제거, 유효성 검사 제거, 다른 세션 작업 허용, 명령 행 존재 의존, event 재시도 비교 제거), 처음에 한 가지(다른 세션의 작업이 명령을 가진 경우)가 걸러지지 않아 테스트를 추가했다.

## 중요 이벤트(특히 `left`)의 보존 정책 — 분석과 방식 C (적용됨)

> 상태: **방식 C(열린 세션당 `left` 1칸 예약)와 오류 구분·`health.json` 을 2026-11-02 사용자 승인으로 적용했다**(변경 기록 "보완 4"). 아래 분석(비교·시나리오·테스트 계획 L1~L10)은 적용 전 분석 그대로이고, 적용 범위는 6번의 1·2번 항목이다. 3번(한도 상향·디스크 여유 하한·구조 파일)과 E·G 방식은 적용하지 않았다. 처음 작성된 상태 문구는 다음과 같다: **분석만, 장비 코드는 바꾸지 않았다.** 사용자 결정(2026-11-02): `left` 를 메모리에만 남기는 방식은 재시작에 유실되므로 단독 해결책으로 쓰지 않는다. 서버의 사건 종료 규칙은 바꾸지 않는다. 승인 전에는 구현하지 않는다.

**1. 무엇이 문제인가 (코드 근거)**
- 사건은 서버가 빈 자리로 판정할 때만 닫힌다(ADR 0005). 거절된 `left` 는 서버가 출차를 모르게 한다. 빈 자리 동안 장비는 사진 없이 Heartbeat 만 보내 신호가 살아 있으므로 SIGNAL_LOST 도 없다. 그래서 사건이 열린 채 남는다.
- 더 큰 영향: 열린 사건이 있으면 다음 차량의 위반 판정은 새 사건이 아니라 "계속 있는 차량" 으로 세어진다(`record_verdict` 의 규칙 2). 즉 **다음 차량의 위반이 별도로 기록·알림되지 않고 이전 사건에 합쳐질 수 있다.** LED 도 켜진 채 남는다.
- 거절의 영향 순서: `left`(위 내용) > `arrived`(다음 refresh, 최대 10분까지 감지 지연) > `confirm`(서버가 명령을 만료까지 다시 보낸다) > `refresh`(다음 주기).

**2. 용량 숫자 (측정 + 추정)**
- 보내는 사진은 330~490 KB가 대부분이고 최대 1,036 KB다(샘플 6장을 실제 `load_jpeg` 로 1280px·품질 92 로 줄여 측정). 20건 ≈ 7~21 MB 이므로 바이트 한도 50 MB 보다 **건수 한도 20 이 먼저 닿는다.**
- 중요 이벤트는 최대 30분(포기 기준) 슬롯을 쓴다. 점유 판정이 흔들려 진입(3프레임=15초)·출차(6프레임=30초)가 반복되면 한 쌍이 약 45초이므로 **20건은 약 7.5분의 단절로 찬다**(추정, 측정 아님). 정상 운영의 한 주차면에서는 거의 도달하지 않는다.

**3. 논리 한도와 실제 디스크는 다른 문제다**

| 구분 | 원인 | 지금 | 예약으로 해결되는가 |
|---|---|---|---|
| 논리 한도 | 건수 20 / 바이트 50 MB | `OutboxFull` | 된다 (정책 값이므로 칸을 미리 비워 둘 수 있다) |
| 실제 디스크 | 디스크 가득, 읽기 전용 파일 시스템, 입출력 오류 (`OSError`) | `OSError` | **안 된다** (공간이 없으면 쓸 수 없다) |

지금은 둘 다 같은 `store_failures` 와 로그 한 줄이라 대응이 갈리지 않는다(앞은 한도 조정이나 단절 해소, 뒤는 디스크 정리·교체).

**4. 방식 비교**

| 방식 | 내용 | `left` 가 논리 한도로 거절되지 않음을 보장? | 대가·위험 |
|---|---|---|---|
| A. 건수 한도 상향(20→40~60) | 값만 바꾼다. 바이트 50 MB 는 유지 | 아니오 (포화가 7.5분 → 15~22분으로 늦춰질 뿐) | 의미 변화 없음. 가장 작은 변경 |
| B. 등급별 고정 예약 | 예: `left` 전용 4칸 | 4칸이 찰 때까지 | `arrived`·`confirm` 이 그만큼 일찍 거절. 칸이 소진될 수 있다 |
| **C. 열린 세션당 `left` 1칸 예약 (추천)** | 점유 중인 차(열린 세션)는 한 번에 최대 하나이므로 `left` 가 아닌 항목은 "마지막 한 칸(과 사진 1장 분량의 바이트)" 을 쓰지 못한다. 새 `arrived` 는 자기 `left` 칸까지 2칸이 비어 있을 때만 받는다 | **예** (논리 한도로는 거절될 수 없다. 세션당 1칸이라 소진되지 않는다) | `arrived`·`confirm`·`refresh` 가 한 칸 일찍 거절된다. 예약은 장비 상태(`occupied`)에 의존한다 |
| D. 중요 이벤트끼리 우선 퇴출 | `left` 가 오면 가장 오래된 `confirm`·`arrived` 를 지운다 | 예 | **사용자 결정("arrived·confirm·left 는 용량 때문에 지우지 않는다")과 충돌**하므로 승인 없이 불가. `confirm` 을 지우면 `executed.json` 때문에 같은 명령을 다시 실행하지도 않아 그 confirm 이 영구 유실 |
| E. 사진 없는 영속 의도 기록(journal) | 거절된 이벤트를 수백 바이트 파일로 남겼다가 자리가 나면 새로 촬영해 전송 | 재시작에도 남는다 | 재촬영 시점의 의미(`left` 는 그때 빈 자리여야 함), 순번·세션 처리, 검증 부담이 크다. C 로 부족하다는 증거가 나온 뒤에 |
| F. 서버의 대체 종료 규칙 | Heartbeat 의 `occupied=false` 가 일정 시간 이어지면 닫는다 | 해당 없음 | **사건 종료 규칙(ADR 0005) 변경**이다. 이번 범위 밖(열린 질문 1번) |
| G. 디스크 여유 확인 + 구조 파일 | 쓰기 전 여유를 확인하고, 중요 이벤트는 더 낮은 하한까지 허용, 시작 때 만든 작은 구조 파일을 `ENOSPC` 때 지우고 재시도 | 물리 디스크 부족에만 해당 | 로그가 디스크를 채우는 경우가 근본 원인이므로 로그 크기 제한이 먼저 |

**5. 시나리오 검토** (현재 정책 / 추천안 C + 오류 구분)

| 시나리오 | 현재 | 추천안을 적용하면 |
|---|---|---|
| 장비 재시작 | Outbox 파일은 남아 순서·내용이 유지된다. 카운터(`store_failures`)와 마지막 오류는 메모리라 사라진다 | 예약은 `occupied`(메모리)에 의존하므로 부팅 직후 점유가 확정되기까지(약 15초)는 보호가 없지만, 그동안 새로 들어가는 항목이 없다. 카운터·마지막 오류를 `outbox/health.json` 에 원자적으로 기록해 재시작 뒤에도 남긴다 |
| 장시간 단절 | 중요 이벤트도 30분이 지나면 포기되어 `dead/` 로 간다. **포기된 `left` 도 사건을 열어 둔다** (용량과 별개의 손실 경로) | 포기 기준은 설계 6.10 그대로. `left` 만 예외로 둘지는 사용자 결정 사항. 포기된 `left` 는 로그·지표로 드러낸다 |
| 연속 출차 (A 출차 → B 진입 → B 출차) | 포화 중이면 B 의 `arrived` 가 거절될 수 있다 | `left_A` 가 저장된 뒤에야 B 의 `arrived`(2칸 필요)를 받는다. 포화 직전이면 B 의 감지는 refresh(≤10분)로 늦어지지만 A 의 출차는 보장 |
| 예약 소진 | 해당 없음 | 논리 예약은 세션당 1칸이라 소진되지 않는다. 물리 디스크 부족은 예약으로 못 막으므로 구분된 오류와 G |

**별도 관찰 (이번 변경과 무관, Phase 1 에도 있던 동작)**: 장비가 꺼진 동안 차가 떠나고 빈 자리로 부팅하면 "부팅 직후 빈 자리: 사진 없이 Heartbeat 만" 이라 `left` 가 가지 않아 서버 사건이 열린 채 남는다. 종료 규칙을 바꾸지 않고는 해결되지 않는다(위 F). 기록만 해 둔다.

**6. 추천하는 최소 변경안 (미적용)**
1. **C**: `Outbox.put(item, reserve=True/False)`. 장비가 열린 세션 중이고 항목이 `left` 가 아니면 `reserve=True`. 계획 단계에서 필요한 빈 칸을 "새 항목 + 예약 1칸", 바이트는 "새 사진 + 사진 1장 분량(고정 2 MB)" 으로 계산한다. 오래된 `refresh` 정리는 그대로.
2. **오류 구분과 지속 기록**: `OutboxFull(reason="items"|"bytes")` 와 `OSError(errno)` 를 구분하고 카운터를 `full` / `disk` 로 나눠 `outbox/health.json` 에 기록.
3. (증거가 생기면) 건수 한도 20 → 40, 디스크 여유 하한과 구조 파일(G).

바꾸지 않는 것: 서버의 사건 종료 규칙, "`arrived`·`confirm`·`left` 는 용량 때문에 지우지 않는다" 는 정책.

**7. 테스트 계획 (구현할 때 먼저 쓸 것)**
- L1 열린 세션이 있으면 `refresh`·`confirm`·`arrived` 는 마지막 한 칸을 쓰지 못하고(사유 `items`), 그 칸에 `left` 는 들어간다.
- L2 새 `arrived` 는 2칸이 비어 있어야 들어간다. 1칸만 남으면 거절되고 `left` 칸은 그대로다.
- L3 `left` 로 세션이 닫히면 예약이 풀린다. 연속 출차(A→B)에서 `left_A` 저장 뒤에 `arrived_B` 가 2칸 규칙을 따른다.
- L4 바이트 예약도 같은 규칙(큰 사진 1장 분량).
- L5 `refresh` 정리는 새 항목의 자리는 만들지만 예약 칸은 만들어 주지 않는다. 정리해도 안 되면 아무것도 지우지 않는다(기존 정책 유지).
- L6 재시작: 같은 Outbox 로 새 runner 를 띄워도 항목의 순서·내용이 같고, `health.json` 의 카운터가 복원된다.
- L7 장시간 단절(가짜 시계): 포화까지 진행해도 `left` 는 거절 0건. 30분 포기가 `left` 를 `dead/` 로 보내는 현재 동작을 명시적으로 고정한다.
- L8 `ENOSPC`(fsync 오류 주입): 사유가 `disk` 로 구분되고 기존 항목과 `refresh` 는 그대로, 예약은 건드리지 않는다.
- L9 점유 판정 흔들림(`arrived`·`left` 반복) 시뮬레이션: 서버로 간 `left` 수 = 보낸 `arrived` 수, `left` 거절 0.
- L10 회귀: 기존 포화 정책 테스트 11개와 장비 테스트 전체.

**결정 결과 (2026-11-02)**: (i) C 채택·구현 승인 → 적용. (ii) 오류 구분·`health.json` → 적용. (iii) 30분 포기에서 `left` 예외 → **이번에는 바꾸지 않고 미해결 위험으로 기록**. (iv) 장비 재시작 중 출차 → **이번 범위에서 종료 규칙을 바꾸지 않는다(미해결 위험으로 기록)**.

**테스트 대응 (L1~L10)**: L1·L2·L3·L4·L5 → `device/test_outbox_reservation.py` 의 같은 이름의 테스트, L6 재시작, L7 점유 판정이 흔들리는 20분 단절(건수 한도를 홀수 19 로 두어 예약이 없으면 드러나게 했다)과 30분 포기의 현재 동작 고정, L8 `ENOSPC`·`EROFS`·`EIO` 주입, L9 연속 출차·흔들림(L3·L7), L10 기존 테스트 전부 통과.

## 10단계 AWS 인프라 사전 검토 (2026-11-03, 코드 분석만, AWS 변경 없음)

Terraform 코드(data: SQS FIFO 2개 + inbox 수명 주기, cluster: worker·relay 역할)를 쓴 뒤 사용자 요청으로 기존 코드와 대조했다. **설계는 바꾸지 않았고**, 아래는 사실과 사용자 결정이다.

**결정 (사용자, 2026-11-03)**: 사진 버킷 `violations/` 의 90일 수명 주기(Lifecycle)는 **보류한다.** 앱의 이미지 만료 처리(`image_status` `EXPIRED`, 지금은 `IMAGE_RETENTION_DAYS` 로 만료 시각만 기록)와 관리자 화면의 만료 사진 표시가 끝난 뒤에 적용한다. 그 전에 객체를 지우면 화면이 "사진 있음"으로 보이는데 열면 실패한다. 지금 Terraform 은 `inbox/` 7일 규칙과 미완료 멀티파트 정리만 가진다.

**확인한 사실 (코드 근거)**

| 항목 | 사실 |
|---|---|
| 보존 기간의 순서 | 본 큐 4일 < `inbox/` 7일 < 작업 행 30일(끝난 작업만 삭제), DLQ 4일(FIFO 는 DLQ 로 옮길 때 보존 시계가 다시 시작된다고 문서에 있음 → AWS 에서 확인). 본 큐 보존이 `inbox/` 보다 길어지면 메시지가 사진보다 오래 살아 `rejected(missing_image)` 가 늘어난다 |
| `queued` 작업의 메시지가 만료·유실되면 | **복구되지 않는다.** `publish_pending` 은 `pending_publish` 만 고르고(`relay.py` 91·103행) `queued` 를 되돌리는 코드가 없다. Worker 는 메시지가 와야만 움직인다. 작업은 `queued` 로 남고, `clean_up` 은 끝난 작업(`FINISHED`)만 지우므로 행도 영원히 남는다 |
| 같은 구멍 | ① `processing` 중 Worker 가 죽었고 그 사이 메시지도 사라진 경우 ② 작업이 DLQ 에 갔는데 Relay 가 4일 넘게 멈춰 DLQ 메시지가 만료된 경우(작업은 `dead_lettered` 가 되지 못하고 `queued`/`processing` 으로 남는다) |
| `inbox/` 가 지워진 작업을 redrive 하면 | `dead_lettered → pending_publish → queued` 뒤 Worker 가 `storage.read` 에서 `FileNotFoundError` → `rejected`(`last_error=missing_image`), 메시지 삭제. 결과 행·위반·순서 번호 갱신 없음. 사건은 장비의 다음 `refresh`(10분) 또는 신호 끊김 규칙으로 따라잡는다 |
| 이 결과가 보이는 조건 | S3 호출자에게 `s3:ListBucket` 이 있어야 없는 객체가 404 로 온다. 없으면 403 이라 Worker 는 영구 오류를 일시 오류(`retry`)로 보고 DLQ 로 보낸다. 그래서 api·worker·relay 에 `ListBucket` 을 줬다 |
| redrive 의 유효 기간 | `inbox/` 만료까지(접수 후 7일). `dead_lettered` 작업 행은 지워지지 않으니 8일째 이후 redrive 는 항상 `rejected` 가 된다 |

**권장 최소 해결안 (구현 전, 사용자 승인 필요)**: Relay 에 "멈춘 작업 재발행" 단계를 추가한다. `queued`, 또는 리스가 끝난 `processing` 이면서 마지막 갱신이 **하루**(본 큐 보존 4일, `inbox/` 7일보다 충분히 짧은 값, 설정값) 넘은 작업을 `pending_publish`(`next_publish_at` = 지금)로 되돌린다. 5분 중복 제거 창은 이미 지났고, Worker 는 이미 끝난 작업의 메시지를 `already` 로 지우므로 두 번 처리되지 않는다. 한 단계가 위 세 구멍(메시지 만료, Worker 사망 중 유실, DLQ 만료)을 함께 덮는다. 보완으로 CloudWatch 경보(`ApproximateAgeOfOldestMessage`, DLQ 깊이)를 둔다. **이 단계가 들어가기 전에는 Worker 를 4일 넘게 멈추지 않는 것이 운영 조건이다.**

### 멈춘 작업 복구 구현 (2026-11-03, 사용자 승인, 로컬 코드·테스트만, AWS 변경 없음)

`OutboxRelay.recover_stalled()` (`backend/app/services/relay.py`). `run_once` 의 첫 단계라 되돌린 작업이 같은 회차에 발행된다. 새 마이그레이션·컬럼은 없다.

| 항목 | 정의 |
|---|---|
| 대상 `queued` | `COALESCE(published_at, updated_at) ≤ now − 임계값`. `published_at` = 마지막으로 **확인한** SQS 전송 시각 = 그 메시지의 SQS 보존 시계 시작점(수신해도 초기화되지 않음). 접수·Relay 의 `_mark_queued` 가 갱신하므로 재전송 때마다 새로 시작 |
| 대상 `processing` | `COALESCE(lease_until, updated_at) ≤ now − 임계값`. 리스가 끝난 시점 = Worker 가 마지막으로 살아 있던 증거. 유효한 리스는 미래 시각이라 절대 걸리지 않는다 |
| 제외 | `pending_publish`(Relay 가 이미 발행 중), `dead_lettered`(수동 `flask jobs redrive` 만), `done`/`stale`/`rejected` |
| 임계값 | 기본 1일(`RELAY_STALLED_AFTER_SECONDS=86400`). 정상 처리(리스 55초, 가시성 60초)보다 훨씬 길고 SQS 보존 4일·`inbox/` 7일보다 훨씬 짧다. **10분 미만은 거부한다**(SQS 중복 제거 5분 창 안의 재전송은 조용히 버려지기 때문) |
| 되돌릴 때 | `pending_publish`, `next_publish_at = 지금`, `claim_attempt + 1`, 리스 비움, `last_error = recovered: ...`. 장비·세션·`seq`·`event`·`created_at` 은 건드리지 않아 순서 가드(`seq > last_applied_seq`)가 그대로 판정한다 |
| claim 펜싱 | Worker 의 `_apply` 는 `status = processing` 이고 자기 `claim_attempt` 와 같을 때만 반영한다. 복구는 상태를 바꾸고 시도 번호를 올리므로 뒤늦게 돌아온 옛 Worker 의 결과는 버려진다 |
| 동시성 | 후보를 읽고, 작업마다 inbox 확인 뒤 **같은 대상 조건을 다시 건 조건부 UPDATE** 한 번으로 바꾼다. 그 사이 Worker 가 claim 했거나 다른 Relay 가 먼저 복구했으면 조건이 맞지 않아 0행이다(Relay 여러 개와 살아 있는 Worker 가 동시에 있어도 한 작업은 한 번만 복구) |
| inbox 사진이 없으면 | 복구하지 않고 바로 `rejected` / `missing_image: inbox photo gone before recovery`. Worker 가 만드는 끝 상태와 같다. 확인 중 저장소 오류면 건드리지 않고 다음 회차에 다시 한다(`storage_errors`) |
| 끝 상태 | 복구된 작업은 `done`/`stale`(순서 뒤바뀜), `rejected`, 또는 계속 실패하면 3번 수신 뒤 DLQ → `dead_lettered`(명시적 실패, 복구 대상이 아님)에 도달한다. 무한 복구 루프는 없다 |
| 순서 | 복구된 옛 작업의 새 메시지는 그 장비 그룹의 맨 뒤에 들어간다. 그 사이 더 새 `seq` 가 반영됐다면 옛 작업은 `stale`(판정은 기록, 사건 상태는 불변)이 된다. 기존 순서 가드의 정상 동작이며 두 번째 사건 변경은 생기지 않는다 |
| 중복 메시지 | 옛 메시지가 아직 큐에 있으면 같은 작업의 메시지가 둘이 된다. 먼저 처리된 쪽이 `done`, 나중 쪽은 `already` 로 지워진다(결과 행 하나) |

**알려진 한계 (해결로 표시하지 않음)**
- 복구는 Relay 가 살아 있어야 한다. Relay 가 임계값보다 오래 멈추면 그동안은 복구되지 않는다(보존 4일 안에는 돌아와야 한다).
- `redrive` 는 inbox 사진 확인을 하지 않는다. 사진이 이미 지워진 `dead_lettered` 작업을 redrive 하면 Worker 가 `rejected(missing_image)` 로 끝낸다(접수 후 7일이 지나면 항상).
- 임계값은 설정값이지만 SQS 보존·inbox 보존과의 관계를 코드가 알지는 못한다(Terraform 은 `inbox_retention_days > judgement_retention_days` 만 plan 에서 검증한다). 값을 바꿀 때 순서(10분 ≤ 임계값 < 4일 < 7일)를 사람이 지켜야 한다.
- 매 회차 후보 최대 50건을 읽는다. 대량 정체가 있으면 여러 회차(2초 간격)에 걸쳐 복구된다.

**redrive 직후 재발행이 SQS 중복 제거 창 경계에서 버려지던 문제 (기존 동작, 2026-11-03 사용자 승인으로 수정: 아래 "redrive 60초 여유")**
- 재현(`faults3b.py`, ElasticMQ): 작업 접수 08:16:28.141 → 저장소 단절로 DLQ → 08:19:29 `dead_lettered` → 즉시 `flask jobs redrive` → Relay 발행 08:21:28.551 (= 접수 + 5분 0.41초). 큐는 비었고 작업은 `queued` 로 남았다. 같은 작업을 `pending_publish` 로 되돌려 다시 발행하자 21초 만에 `done`.
- 원인(추정, 코드로 확인): `redrive()` 는 다음 발행을 `마지막 전송 시각 + 5분` 으로 잡는데 마지막 전송 시각을 `published_at` 또는 `created_at` 으로 쓴다. 실제 SQS 전송은 그보다 약간 뒤(행 생성 → 커밋 → 전송)라서 여유가 0 이면 5분 창이 아직 끝나지 않은 순간에 보낼 수 있고, 그 메시지는 조용히 버려진다. 이 조용한 유실이 바로 `redrive` 의 주석이 막으려던 상태("`queued` 로 남아 메시지가 없다")다.
- 영향: redrive 한 작업이 최대 임계값(1일) 동안 `queued` 로 정체했다가 복구 단계가 구해 준다. 데이터 손실은 없다.
- 최소 해결안: `redrive` 의 대기에 60초 여유를 더한다. 아래 "redrive 60초 여유"에서 적용 결과를 적는다. 복구 임계값(1일)은 이를 보완하지만 대체하지 않는다.

### redrive 60초 여유 (2026-11-03, 사용자 승인, 로컬 코드·테스트)

`next_publish_at = max(지금, 마지막 전송 + 5분 + 60초)` (`REDRIVE_MARGIN`, `backend/app/services/relay.py` `redrive()`).

**마지막 전송 시각의 기록과 실제 전송의 차이 (코드로 확인)**

| 경로 | `published_at` 을 쓰는 때 | 실제 SQS 전송과의 관계 |
|---|---|---|
| 접수 API(`ingest._publish_now`) | 전송이 **끝난 뒤** `utcnow()` | 기록이 전송보다 늦다 → 5분 계산에 안전한 쪽 |
| Relay(`_publish_machine`) | 회차 **시작** 시각 `now` | 기록이 전송보다 이르다(같은 배치의 앞선 전송, 느린 호출만큼). 5분을 정확히 더하면 창 안에 들어갈 수 있다 |

접수 경로로 발행된 작업은 원래도 안전했고, Relay 가 발행한 작업(접수 전송이 실패했거나 Relay 가 먼저 잡은 경우)이 경계에서 위험했다. 관찰된 사례: 접수 08:16:28.141, redrive 발행 08:21:28.551(접수 + 5분 0.41초)에서 ElasticMQ 가 버렸다.

**60초 여유가 보장하는 것과 한계**
- 보장: 기록과 실제 전송의 차이가 60초 **미만**이면 redrive 재발행은 중복 제거 창 밖이다. 정상 운영의 차이는 밀리초~수 초다.
- 한계: ① 차이가 60초 이상이면 여전히 버려질 수 있다(한 회차에 느린 전송이 많은 배치; Relay 는 회차당 최대 50건). ② `published_at` 이 없어 `created_at` 으로 계산한 작업은 생성과 전송 사이가 길면 같은 위험이 있다. ③ 이 값은 SQS 가 5분 창을 어떻게 재는지(실제 AWS 는 첫 전송부터 5분)를 에뮬레이터로만 확인한 것이다. 실제 AWS 에서 재확인한다.
- 그물: 위 한계로 메시지가 버려지면 작업은 `queued` 로 남고, 1일 뒤 멈춘 작업 복구가 다시 발행한다(테스트로 고정).
- 근본 해결안(적용하지 않음): Relay 가 `published_at` 을 전송 **뒤** 시각으로 기록하면 두 경로가 같아진다. 복구 임계값(`published_at` 기준)의 의미는 바뀌지 않는다. 동작 변경이라 별도 승인이 필요하다.

**검증 결과**
- 테스트(먼저 작성, 여유 없는 상태에서 동작 실패 6개를 확인한 뒤 구현): 새 테스트 17개(SQLite 17, PostgreSQL 19: 두 redrive 동시 실행, Relay 4개 동시 발행). 경계 직전(4분 59초)·직후(5분 1초)·5분 59초·정확히 6분·6분 1초·10분·2일, Relay 가 6분 전에는 보내지 않음, 옛 메시지가 남은 상태의 중복 메시지(`done` + `already`, 결과 1), Relay 재시작(예약이 DB 에 있음), CLI 두 번 실행, 장비별 발행 순서(앞선 작업이 막고 있으면 뒤 작업도 대기), 메시지가 그래도 버려진 경우 1일 복구.
- 결함 주입 4가지(여유 0, 30초, `max`→`min`, `created_at` 만 사용)를 모두 잡았다.
- 전체: SQLite 523 통과(건너뜀 30), PostgreSQL 553 통과(건너뜀 0), 장비 97 통과.
- Compose(ElasticMQ, `faults3b.py`): 접수 09:26:11.322 → 저장소 단절로 DLQ → `dead_lettered` → redrive. 예약 `next_publish_at` 09:32:11.334(접수 + 6분 0.012초), Relay 발행 09:32:13.088, `done` 09:32:23.867. 같은 시나리오가 수정 전에는 `queued` 에서 멈췄다. **주의**: 한 번은 PC 절전(Modern Standby, 18:03~18:25)으로 Docker VM 이 멈춰 발행이 19분 늦어졌고(그 실행은 검증에서 제외), 절전을 막고 다시 실행했다.
- 이 수정은 "경계에서 버려지는 문제"가 사라졌다는 증거이지 60초가 최소값이라는 증거는 아니다.

**운영 관측 지표와 경보 후보 (CloudWatch 는 아직 만들지 않음)**

`flask outbox-relay` 는 회차마다 `stats` 를 만든다(`--once` 는 출력). 상시 루프에서는 로그로 나가므로, 지표는 로그 지표 필터(Logs Metric Filter) 또는 큐 기본 지표로 얻는다.

| 보고 싶은 것 | 어디서 | 경보 후보 |
|---|---|---|
| 멈춘 작업 수 | `stalled_jobs` (복구 뒤에도 남은 수). 로그 `stalled jobs remain after recovery: N job(s)` | 5분 이상 1 이상 |
| 가장 오래된 미완료 작업의 나이 | `oldest_open_job_age_seconds`(`pending_publish`·`queued`·`processing` 중 `created_at` 최소). 같은 로그 줄에 포함 | 1시간 초과 경고, 12시간 초과 긴급 |
| 복구 횟수 | 로그 `job <id> recovered: requeued\|rejected (was queued\|processing)` 줄 수 | 하루 1건 이상이면 원인 조사(정상 운영에서는 0이어야 한다) |
| 복구 불가(저장소 오류) | 로그 `recovery cannot check the inbox photo` | 연속 3회 이상 |
| 큐 정체 | SQS 지표 `ApproximateAgeOfOldestMessage`(본 큐) | 1시간 초과(보존 4일의 안전 여유) |
| DLQ | SQS 지표 `ApproximateNumberOfMessagesVisible`(DLQ) | 1 이상 |
| 오래된 pending_publish | 기존 로그 `pending_publish older than 5 min` | 기존 설계(5분) |
