# 0002. 조회는 회사 전체, 구조 변경은 서비스 운영자만

- 상태: 결정됨 (2026-10-01)

## 문제

처음 구현에서는 회사 관리자가 자기 회사의 주차장 생성, 구역 추가, 장비 등록, 인증 키 재발급, 담당 관리자 변경을 모두 할 수 있었다. 그래서 알림을 받기 싫은 관리자가 자기 자신을 담당에서 빼 버리거나, 동료의 담당을 임의로 바꿀 수 있었다. 장비 인증 키도 누구나 재발급할 수 있어 운영 중인 장비가 끊길 수 있었다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 주차장 메뉴 전체를 서비스 운영자만 보게 한다 | 회사 관리자가 다른 주차장의 담당자와 장비 상태를 볼 수 없게 된다. 회사 전체 현황을 볼 수 있어야 한다는 요구와 충돌한다 |
| 목록은 보여 주되 자기 담당 주차장만 들어갈 수 있게 한다 | 문제는 "어느 주차장에 들어가느냐"가 아니라 "들어가서 무엇을 바꾸느냐"다. 담당자는 여전히 자기 주차장에서 스스로를 담당에서 뺄 수 있다 |
| 조회와 변경을 나눈다 | 채택 |

## 결정

**조회는 회사 전체, 변경은 서비스 운영자만.**

| 기능 | 회사 관리자 | 서비스 운영자 |
|---|---|---|
| 자기 회사의 주차장, 구역, 장비, 담당자 조회 | 가능 | 가능 |
| 주차장과 구역의 생성과 수정 | 불가 | 가능 |
| 장비 등록, 수정, 인증 키 재발급 | 불가 | 가능 |
| 담당 관리자 배정 변경 | 불가 | 가능 |
| 위반 확인과 처리 완료 | 가능 | 가능 |

화면에서 버튼을 숨기는 것으로 끝내지 않고 서버 API 여덟 개에서 Role을 검사한다.

## 이유

- 장비를 현장에 설치하고 등록하고 신호를 확인하는 일은 서비스 쪽이 한다. 등록 주체도 같아야 한다.
- 장비 인증 키는 자격 증명이다. 볼 수 있는 사람이 적을수록 좋다.
- 주차장과 장비 수는 계약과 연결된다.
- 관리자 계정 생성이 이미 서비스 운영자 전용이다. 계정을 만들 때 담당 주차장도 함께 정하는 흐름이 일관된다.

## 결과

- 얻은 것: 담당자가 스스로 알림 대상에서 빠지는 일을 막았다. 변경 주체가 하나라 감사 로그 추적이 쉽다.
- 감수한 것: 고객사에서 근무자가 바뀔 때마다 서비스 운영자에게 요청해야 한다. 고객사가 늘면 운영자가 병목이 된다.
- 이후: 병목이 실제 문제가 되면 회사 안에 대표 관리자 역할을 두고 담당 배정만 맡기는 방안을 검토한다. 지금은 Role을 두 개로 유지한다.

## 근거

- 서버 검사: `backend/app/api/parking.py`, `backend/app/api/admins.py` 의 `require_auth(Role.SUPER_ADMIN)`
- 테스트: `backend/tests/test_permissions.py`. 회사 관리자의 변경 시도 8가지가 모두 403이고 데이터가 그대로인지, 담당이 아닌 주차장도 조회되는지 검증한다
- 화면: `frontend/src/pages/company/ParkingLotDetail.js` 의 `canEdit`

## 한 줄 설명

"어느 주차장을 보느냐"가 아니라 "무엇을 바꾸느냐"로 권한을 나눠, 회사 관리자는 회사 전체를 읽고 구조 변경은 서비스 운영자만 하도록 서버에서 강제했습니다.
